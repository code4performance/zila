Tasks and channels

A task is a function running next to the others. Tasks talk through channels. They are lightweight (thousands are fine), cooperative, and share one scheduler with async/await.

spawn and channel

spawn f(x) starts f as a new task. channel(T) makes a channel carrying values of type T; send puts a value in, receive waits for one, close ends the stream.

use task

func worker(id: int, jobs: Channel<int>, results: Channel<text>)
    while true
        let n = jobs.receive()
        if n == 0
            return
        end
        results.send("worker {id} squared {n} = {n * n}")
        task.yield()
    end
end

func main()
    let jobs = channel(int)
    let results = channel(text)
    spawn worker(1, jobs, results)
    spawn worker(2, jobs, results)
    for i in 1..5
        jobs.send(i)
    end
    jobs.send(0)
    jobs.send(0)
    for i in 0..4
        print(results.receive())
    end
end

Threads

Tasks share one thread. To use a second core, start an operating-system thread: spawn_thread f(args) evaluates the arguments here, then runs f on a new thread and gives back a Thread. t.join() waits for it. Threads are heavy (an operating-system stack each): use them for parallel work, not for thousands of small jobs.

use thread
use sync

func count(hits: shared sync.Atomic)
    for i in 0..100000
        hits.add(1)
    end
end

func main()
    let hits = shared sync.Atomic{ value: 0 }
    let a = spawn_thread count(hits)
    let b = spawn_thread count(hits)
    a.join()
    b.join()
    print("{hits.load()}")    // 200000
end

shared: data that several threads read

shared expr makes a record, list, map or text whose reference counts are atomic; the type is written shared T. Its content is immutable: s.count = 1 or s.items.add(1) through a shared value is a compile error that suggests Mutex<T>. A program that never uses shared or spawn_thread keeps plain, non-atomic counts and runs the same code as before; one that does counts every reference atomically (the runtime's counters get a lock prefix).

Mutex and Atomic

use sync gives Mutex<T> and Atomic. shared sync.Mutex(value) guards a value: m.update(func(v) ... end) replaces it under the lock, m.get() and m.set(v) read and write it, m.with(f) calls f with it. To hold the lock over several statements use m.lock(), defer m.unlock() and m.locked_get() / m.locked_set(v). A thread that waits for a lock sleeps in the kernel; locking a mutex the thread already holds stops the program with the mutex is already locked by this thread. Atomic is one long with load, store, add (returns the previous value), swap and compare_swap, all sequentially consistent.

What may cross to another thread

The compiler decides from the types, with no annotation. Transferable: numbers, bool, char, text, enums, closures, Thread, Mutex and Atomic, and records, lists, maps, channels and results of transferable types. Not transferable: Rc<T> (new T), Weak<T>, raw pointers and futures. Every argument of spawn_thread, every variable a closure passed to it captures, and the value after shared is checked, and the error names the argument, the field path and the type:

argument 'job': field 'job.owner.next' has type 'new Node', which is not transferable between threads: it cannot be used by another thread; share data between threads with `shared`, `Mutex<T>` or `Atomic`

A function started with spawn_thread (and the functions it calls by name) may not use a mutable global var unless its type is sync.Mutex or sync.Atomic; let globals are fine.

One scheduler per thread

Each thread has its own scheduler: spawn, async, await, sleep and the file and network libraries work inside a thread and never leave it; a task stays on the thread that created it. Channels are safe for any number of sending and receiving threads: values from one sender arrive in order, each value is received once, receive parks only the receiving task, a send from another thread wakes it on its own thread, and close wakes every receiver. An idle thread sleeps in the kernel (a completion port) and uses no CPU. Deadlock detection is per program: when every live thread is waiting for another one (an idle scheduler with no timer, a join), the program stops with fatal: all tasks are asleep - deadlock!.

The ui library stays on the main thread. abort in a thread stops the whole program with status 101. When main returns the process ends even if threads are still running. thread.id() is the calling thread's identifier and thread.sleep(ms) blocks the whole thread.

How it behaves

  • Tasks of a thread run on that thread and take turns. A task gives up the processor only when it waits (receive, await), calls task.yield(), or finishes. A task that computes for a long time makes the others wait.
  • send never blocks: a channel is an unbounded queue.
  • receive waits for a value. On a channel that is closed and empty it returns 0 (or the empty value of its type). Sending on a closed channel stops the program.
  • If every task is waiting and no timer or file or network operation is in progress, the program stops with fatal: all tasks are asleep - deadlock! and a non-zero exit code.
  • When main returns the program ends, even if tasks are still running.
  • Spawn evaluates the call inside the new task, with the variables it uses captured by value when spawn runs.

Limits

  • Tasks never run at the same instant on one thread; for parallelism use threads.
  • Threads exist on Windows only for now (the Linux thread layer is not written yet); a bare-metal kernel rejects spawn_thread.
  • A mutex is not re-entrant and a task waiting for one blocks its whole thread; there are no condition variables or read-write locks yet.
  • Windows x64 and Linux x86-64 (tasks are fibers on Windows and stack switches on Linux); a bare-metal kernel cannot use them.
  • The ui message loop does not yet run other tasks.

await works in any function and suspends only the current task; drop methods and C callbacks cannot await. For waiting on time, files and the network, use async/await.
