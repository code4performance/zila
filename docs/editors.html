Editors and debugging

The zila program is also a language server (zila --lsp) and a debug adapter (zila --dap). The VS Code extension in editors/vscode connects an editor to both; any editor that speaks the Language Server Protocol or the Debug Adapter Protocol can do the same by starting those commands.

Install the extension

Put zila on your PATH (or set zila.server.path), build the package once and install it with the editor's own command:

cd editors/vscode
npx @vscode/vsce package                                  # writes zila-lang-0.5.0.vsix

code --install-extension zila-lang-0.5.0.vsix             # VS Code
antigravity-ide --install-extension zila-lang-0.5.0.vsix  # Antigravity

VS Code and the editors built on it keep separate extension folders; copying the files into one of them by hand leaves the extension unregistered, because the editor never learns about it. After installing, reload the window (Developer: Reload Window) and open a .zila file. Highlighting works even when the language server is off.

What the language server does

It works on the text in the editor, saved or not, and on the unsaved text of every other open file of the project, without producing an executable. After you stop typing for a moment it checks the program the way a build does.

Errors and warnings
A syntax error is shown alone, on the first one. A text that parses is checked: type mismatches, unknown names, wrong arguments and the other errors of a build appear on the expression they are about, and the warnings of the compiler as warnings. Editing a function in one file updates the errors of the files that use it.
Completion
The names in scope (locals, parameters, functions, types, imported packages), the fields and methods after ., the public members after a package name, the variants after an enum name, and the attributes inside #[. It works while the file has a syntax error elsewhere: what parses is used.
Hover and signature help
Hover shows the type or signature of a name and the // comment above its declaration. Inside a call the signature of the function appears with the parameter you are typing marked.
Go to definition and references
To the declaration in the same file, another file of a package of the project, or the standard library (a read-only copy of its source). References lists every use in the program.
Symbols and rename
The outline of a file and a search of the declarations of the program. Rename changes the declaration and every use, in every file of the project, and refuses with a message when the new name is taken, is not a name, or when the symbol belongs to the standard library or a dependency.

A program that uses code generation (comptime) is not checked by the server: it would have to run that code, and opening a file must never run anything.

Debugging

Press F5 in a .zila file, or add a launch configuration:

{
  "type": "zila",
  "request": "launch",
  "name": "Debug current file",
  "program": "${file}",
  "stopOnEntry": false
}

The adapter builds the program with --debug (a compile error fails the launch with its message), starts it under the debugger and stops at the breakpoints you set in the editor. It supports continue, pause, step over, step into and step out, the call stack with file and line, and stopping when the program aborts or crashes. The program's output appears in the debug console.

  • A breakpoint on a blank or comment line moves to the next line that has code, and the editor shows it there.
  • The Variables view shows the parameters and locals of the selected frame with their types: numbers, text, char and bool as values; records, lists, maps and enums expanded into their parts; errors with their message. A value that cannot be read is shown as unavailable, never as a wrong one. The optimizer keeps some locals in registers, which can only be read in the innermost frame.
  • The debug console evaluates names, field accesses and indexes: p.x, items[2].name, xs.len, m["key"].
  • An abort stops the program with its message and the stack of the call; continuing ends the program with status 101.

The debugger works for programs built for the operating system it runs on (Windows, or Linux through ptrace). Launching a program of the other system fails with a message that says so.

The debug-information file

zila main.zila --debug -o main.exe     # also writes main.zdbg next to it

--debug writes a JSON file next to the executable that maps machine-code addresses to files and lines and describes each function, parameter and local with its name, type and where it lives. The executable is byte-identical with and without the flag: debugging cannot change what the program does. Use it to build a program you want to attach your own tools to; the adapter does it for you when you launch.

Other editors

Start zila --lsp for .zila files in any editor with a Language Server Protocol client. For debugging, start zila --dap in any Debug Adapter Protocol client and send a launch request with program (the .zila file), and optionally args, cwd and stopOnEntry. Both speak on standard input and output.
