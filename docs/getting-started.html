Getting Started

Zila Lang's reference implementation is a Rust lexer, AST, and recursive-descent parser and a native x86-64 compiler — std-only, no external dependencies.

Build

cargo build --release
cargo test

cargo build --release compiles the zila command-line tool; cargo test runs the parser's test suite (precedence, newline rules, match arms, generics, and error-position checks).

Run a program

Once built, point zila at any .zila file:

./target/release/zila examples/rest_api.zila            # OK + summary
./target/release/zila examples/hello.zila --ast          # dump the AST
./target/release/zila examples/hello.zila --tokens       # dump tokens
./target/release/zila examples/hello.zila --run          # compile, run, delete the executable
./target/release/zila run examples/hello.zila            # the same as --run, as a subcommand
./target/release/zila -e 'print(1 + 2)'                  # run code given right here, no file
./target/release/zila examples/async.zila -o async.exe   # compile to a native executable
(no flag)
Parses the file and prints OK <path>: <summary> — a one-line count of packages, uses, functions, types, variables, externs, and embeds. This is the quickest way to check that a file parses without errors.
--tokens
Runs only the lexer and prints every token with its line and column, one per line. Useful for debugging how the lexer splits up a tricky piece of source (string interpolation, newline collapsing, generics closing with >>, etc.).
--ast
Parses the file and pretty-prints the full abstract syntax tree (every statement and expression node, each carrying its source line).
--run
Builds the program into a temporary executable for this machine, runs it with your terminal's input and output, deletes the executable and exits with the program's exit status (101 after an abort). The program is the one -o would build, so every feature works the same way; compile errors are reported as -o reports them and nothing runs. --run only runs programs for the machine it is on: a different --target is rejected.
run file.zila
A subcommand that does exactly what file.zila --run does (and takes --no-opt). run - reads a whole program, with its package line, from standard input.
-e code
Runs code given on the command line, with no file and no boilerplate (also written eval code; eval - reads the code from standard input, for pipes and here-documents). The code is a list of statements, and may mix in use lines and declarations (func, type, extern, embed, attributes). The tool puts the statements in the body of func main() -> error inside package main, so try works, then builds and runs it as --run does. A line that starts in the first column with one of those declaration words, up to the line that is exactly end, is a declaration; everything else is a statement. If the code defines its own func main, it is compiled as written. Errors name the line and column of your code (<eval>:2:10). There is no interactive prompt. 
zila -e 'print("hi")'
zila eval - <<'EOF'
func double(n: int) -> int
    return n * 2
end
print(double(21))
EOF
-o output.exe
Compiles the file to a native Windows x86-64 executable (also written --build). The compiler writes the executable itself, so no other tool (no Visual Studio) is needed. The resulting program has no runtime to install. See Native compilation for what it supports.
--asm
Prints the x86-64 assembly the native compiler generates for the file.
--target windows|linux
Chooses what -o builds: a Windows executable (the default) or a static Linux x86-64 ELF executable written by the compiler alone, with no external tools. With --asm it shows that target's assembly. Linux programs cannot use fs, net, task, ui or extern yet; see Native compilation.
--no-opt
Compiles without the optimizer (see Native compilation). Use it to check whether a problem comes from an optimization: the program must behave the same either way. Combine it with -o or --asm.
--no-prune
Keeps every function, global and string of every library the program names with use, even when nothing reaches it. By default only what the program can reach is in the executable, so a use that is never called costs nothing (see Packages). Use this flag to check whether a problem comes from pruning: the program must behave the same either way.
--explain-link
Prints how many bytes of code and data each package contributes to the program (the program itself, each library or dependency named by use, the runtime, strings and generated helpers), largest first, and the total. It writes no executable unless -o is also given. Combine it with --target linux for the Linux program. See Packages.
--docs
Rewrites the example blocks of this documentation site from examples/*.zila. Run it after changing an example; cargo test fails when the pages are out of date.
--fmt file.zila ...
Rewrites the files in the standard style and prints the names of the ones it changed. Only whitespace changes: four spaces per block level (end and else line up with the line that opens the block), one space after commas, no trailing spaces, at most one blank line in a row, comments kept. It refuses to write a file whose tokens would differ from the original's, and leaves a file with a syntax error alone.
--fmt-check file.zila ...
Changes nothing: lists the files that are not in the standard style and exits with status 1 when there are any (and 0 otherwise), so a build can check formatting.
--test file.zila ...
Builds each file with a generated entry point that runs its #[test] functions in order and prints ok name or FAIL name: message for each, then test result: N passed, M failed. The exit status is 1 when a test failed, a file does not compile or the run stopped early (a crash such as a division by zero is reported with its exit code). The file's own main is not used; combine with --no-opt to test without the optimizer. See Testing.
--lsp
Runs a language server on standard input and output (Language Server Protocol). It reports syntax errors as you type and formats documents in the standard style, like --fmt. Any editor with an LSP client can use it by starting zila --lsp for .zila files.
--comptime-timeout seconds
The time one run of comptime generators may take (default 5). A generator that takes longer is stopped and the build fails with an error naming it. See Compile-time code generation.
--no-comptime-cache
Runs the comptime generators again instead of reusing the results saved by earlier builds (and does not save new ones).
--comptime-dump
Prints the text every comptime generator produced to standard error, so you can see what was compiled.
--init [name]
Writes zila.toml in the current directory. See Packages.
--add git-url[@version]
Adds a dependency to the manifest and fetches it (the newest tag when no version is given). The one command, with --fetch and --update, that uses the network.
--as name
With --add: the import name of the dependency (default: the last part of the URL).
--fetch
Chooses the versions of every dependency, downloads what the cache lacks, checks the hashes and writes zila.lock.
--tidy
Removes the dependencies no source file uses and rewrites zila.lock to the packages that are needed. No network.
--update [name]
Raises the minimum version of a dependency (or all) to the newest tag of its major version, then fetches.
--offline
With the package commands: use only the cache and the lock, and fail naming what is missing. Builds never use the network, so it changes nothing for them.
--os boot.zila kernel.zila -o disk.img
Builds a bootable disk image from a boot sector and a kernel, both written in Zila Lang (see os/ in the repository). Run it with QEMU.

Editor support

The repository has a VS Code extension in editors/vscode: syntax highlighting, syntax errors as you type and Format Document, using the language server (zila --lsp). It has no npm dependencies and needs no build step. Put zila on your PATH (or set zila.server.path), then package and install it:

cd editors/vscode
npx @vscode/vsce package
code --install-extension zila-lang-0.4.0.vsix

The settings are zila.server.path (the executable, default zila), zila.server.enabled and zila.trace (log the protocol to the Zila Lang Language Server output channel), and the command Zila Lang: Restart Language Server. If the executable cannot be started you get one message and highlighting keeps working. Other editors can run zila --lsp with any Language Server Protocol client.

Reading errors

Parse errors report the file, line, and column, with the offending source line and a caret pointing at the problem:

error: expected 'end', found end of file
  --> prog.zila:4:1
