Getting Started

Brasa's reference implementation is a Rust lexer, AST, and recursive-descent parser and a native x86-64 compiler — std-only, no external dependencies.

Build

cargo build --release
cargo test

cargo build --release compiles the brasa-parse command-line tool; cargo test runs the parser's test suite (precedence, newline rules, match arms, generics, and error-position checks).

Run a program

Once built, point brasa-parse at any .br file:

./target/release/brasa-parse examples/rest_api.br            # OK + summary
./target/release/brasa-parse examples/hello.br --ast          # dump the AST
./target/release/brasa-parse examples/hello.br --tokens       # dump tokens
./target/release/brasa-parse examples/hello.br --run          # compile, run, delete the executable
./target/release/brasa-parse examples/async.br -o async.exe   # compile to a native executable
(no flag)
Parses the file and prints OK <path>: <summary> — a one-line count of packages, uses, functions, types, variables, externs, and embeds. This is the quickest way to check that a file parses without errors.
--tokens
Runs only the lexer and prints every token with its line and column, one per line. Useful for debugging how the lexer splits up a tricky piece of source (string interpolation, newline collapsing, generics closing with >>, etc.).
--ast
Parses the file and pretty-prints the full abstract syntax tree (every statement and expression node, each carrying its source line).
--run
Builds the program into a temporary executable for this machine, runs it with your terminal's input and output, deletes the executable and exits with the program's exit status (101 after an abort). The program is the one -o would build, so every feature works the same way; compile errors are reported as -o reports them and nothing runs. --run only runs programs for the machine it is on: a different --target is rejected.
-o output.exe
Compiles the file to a native Windows x86-64 executable (also written --build). The compiler writes the executable itself, so no other tool (no Visual Studio) is needed. The resulting program has no runtime to install. See Native compilation for what it supports.
--asm
Prints the x86-64 assembly the native compiler generates for the file.
--target windows|linux
Chooses what -o builds: a Windows executable (the default) or a static Linux x86-64 ELF executable written by the compiler alone, with no external tools. With --asm it shows that target's assembly. Linux programs cannot use fs, net, task, ui or extern yet; see Native compilation.
--no-opt
Compiles without the optimizer (see Native compilation). Use it to check whether a problem comes from an optimization: the program must behave the same either way. Combine it with -o or --asm.
--docs
Rewrites the example blocks of this documentation site from examples/*.br. Run it after changing an example; cargo test fails when the pages are out of date.
--fmt file.br ...
Rewrites the files in the standard style and prints the names of the ones it changed. Only whitespace changes: four spaces per block level (end and else line up with the line that opens the block), one space after commas, no trailing spaces, at most one blank line in a row, comments kept. It refuses to write a file whose tokens would differ from the original's, and leaves a file with a syntax error alone.
--fmt-check file.br ...
Changes nothing: lists the files that are not in the standard style and exits with status 1 when there are any (and 0 otherwise), so a build can check formatting.
--test file.br ...
Builds each file with a generated entry point that runs its #[test] functions in order and prints ok name or FAIL name: message for each, then test result: N passed, M failed. The exit status is 1 when a test failed, a file does not compile or the run stopped early (a crash such as a division by zero is reported with its exit code). The file's own main is not used; combine with --no-opt to test without the optimizer. See Testing.
--lsp
Runs a language server on standard input and output (Language Server Protocol). It reports syntax errors as you type and formats documents in the standard style, like --fmt. Any editor with an LSP client can use it by starting brasa-parse --lsp for .br files.
--os boot.br kernel.br -o disk.img
Builds a bootable disk image from a boot sector and a kernel, both written in Brasa (see os/ in the repository). Run it with QEMU.

Editor support

The repository has a VS Code extension in editors/vscode: syntax highlighting, syntax errors as you type and Format Document, using the language server (brasa-parse --lsp). It has no npm dependencies and needs no build step. Put brasa-parse on your PATH (or set brasa.server.path), then package and install it:

cd editors/vscode
npx @vscode/vsce package
code --install-extension brasa-lang-0.2.0.vsix

The settings are brasa.server.path (the executable, default brasa-parse), brasa.server.enabled and brasa.trace (log the protocol to the Brasa Language Server output channel), and the command Brasa: Restart Language Server. If the executable cannot be started you get one message and highlighting keeps working. Other editors can run brasa-parse --lsp with any Language Server Protocol client.

Reading errors

Parse errors report the file, line, and column, with the offending source line and a caret pointing at the problem:

error: expected 'end', found end of file
  --> prog.br:4:1
