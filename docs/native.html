Native compilation

The Zila Lang compiler turns a program straight into x86-64 machine code. There is no C, no Rust and no virtual machine in between, and the program needs no runtime installed: a console program is a few kilobytes and imports only the Windows libraries it uses.

Build a program

zila-parse examples/hello.br -o hello.exe
./hello.exe

The compiler writes assembly, assembles it with its own assembler and writes the Windows executable (PE) itself: it needs no Visual Studio, ml64 or link, and starts no other program. Imports come from each #[link("library")] (#[link_src], which compiles C files, is an error on Windows). Windows x64 is the only target for programs; Zila Lang OS uses a second, bare-metal target. --asm prints the generated assembly instead of building.

The executable holds everything the program uses: the libraries named with use are compiled in, only what the program can reach is kept, and nothing is loaded from source or from a cache when it runs. --explain-link prints how many bytes each package adds. See Packages.

What works

  • Integers (int = i32, long = i64, byte, and sized types such as u16 or usize for low-level code; lengths and indices are int, sizes and offsets of files are long), bool, text with {interpolation}, []T lists and raw pointers.
  • record types, methods, default and named arguments, variadic ...T parameters.
  • enum with or without data and match, which must cover every case.
  • Errors: -> T or error, try, error("message"), match with ok(v) and err(e), and ??.
  • Closures (they capture by value) and top-level functions passed to C as callbacks.
  • Generic functions and records with inferred type arguments, and structural interfaces used as bounds (see the syntax guide).
  • float, f64 and f32: arithmetic, comparison, conversion, shortest-text printing, use math, and extern calls (see the syntax guide).
  • Map<K, V>: maps with any Hash key (text, integers, records, enums, lists), literals, m[key], has, get, remove and for in insertion order (see the syntax guide).
  • defer: a call that runs when the function ends, however it ends (see the syntax guide).
  • if as an expression, while, for over ranges, lists and maps, break and continue.
  • unsafe, extern "system" calls, asm blocks and #[naked] functions.
  • Tasks and channels, async/await, files and TCP, and the ui library for native windows.

Memory

Heap values (text, records, lists, closures, enums with data, results, channels, futures) are managed with reference counting. A value is freed the moment the last reference to it goes away, including when a function ends early with return, break or try. There is no garbage collector, so there are no pauses.

  • Records are copied when assigned or passed; ref lends the original for the duration of the call (the callee cannot store, return or capture it; use new T{ ... } for a value that must live longer).
  • Lists and maps have value semantics too: assigning, passing or returning one gives the new holder its own value, also when it sits in a record field. Copying is cheap (the elements are not copied) and writing to a shared list copies it: the first write to a list or map that another holder still has copies it once, and later writes go in place. Pass it as ref when the callee should change the caller's list. A loop over a list keeps visiting the elements it started with, even if its body writes to the list. Closures are shared.
  • new Node{ ... } makes a shared object of type Rc<Node>: copying an Rc (assigning, passing, storing in a list or field, capturing) shares the same object and adds one to its count, and a field written through one name is seen through all. == compares identity. A cycle made only of Rc references is never freed (the language does not detect cycles): break it with Weak<T>, see Shared objects and weak references.
  • live_objects() returns how many heap objects are alive, which makes leaks easy to see.
  • The heap is the default allocator and can be replaced: a program that declares #[allocator(alloc)] and #[allocator(free)] functions (and optionally realloc) gets all its memory from them on every target. The Windows executable then does not import HeapAlloc, HeapFree or GetProcessHeap, and a Linux executable carries no free lists and no mmap code. heap_bytes() is not available then. #[no_alloc] makes the compiler prove that a function allocates nothing. See Attributes.
type Point = record
    x: int
    y: int
end

func main()
    let before = live_objects()
    for i in 0..1000
        let p = Point{ x: i, y: 2 }
        let s = "point {p.x}"
        if s.len == 0
            print("never")
        end
    end
    let left = live_objects() - before
    print("objects left: {left}")        // 0
end

Cleaning up: drop

A record can define a drop method. Zila Lang calls it when the last reference goes away, which is how files and sockets close themselves.

type Handle = record
    id: int
end

func (ref h: Handle) drop()
    print("closing {h.id}")
end

func main()
    let a = Handle{ id: 1 }
    print("working")
end                                   // prints: working, then closing 1

A drop method takes nothing and returns nothing. Records marked #[shared] (used by the standard library for files, sockets and futures) are never copied: every name refers to the same object, and writes to their lists and maps are seen by every name (new T{ ... } makes a shared object that user code can create; #[shared] stays for library records).

Shared objects and weak references

new Node{ value: 1 } allocates one reference-counted object (non-atomic in a program without threads; an Rc is not transferable to another thread) and has type Rc<Node>. The record Node itself stays a value type; only an Rc is shared. new needs a record literal, and an Rc cannot be used where a plain Node is expected.

Weak<T> refers to an object without keeping it alive. weak(x) takes an Rc<T> and returns a Weak<T>; w.upgrade() returns an Rc<T>?, nil once the last strong reference is gone. A Weak<T> may be nil (a root node has no parent) and upgrade() on it returns nil. A child that holds parent: Weak<Node> while the parent holds children: []Rc<Node> is freed completely, which live_objects() shows; two objects that hold each other with Rc fields still leak. A closure holds an Rc it uses strongly and a Weak weakly, so capturing weak(node) breaks the cycle between a node and a callback stored in it.

Memory layout: a shared object is the record followed by one extra word, the cell, which is 0 until the first weak(x). The cell is a small counted heap object holding a pointer to the object; the object owns one reference to it and every Weak value owns another, so a Weak stays valid after the object is freed (and shows up in live_objects() until the last one goes). When the strong count reaches zero the order is: the cell is cleared (so upgrade() is nil from now on, also inside drop), the record's drop method runs once, then the heap fields are released. Releasing a Weak never runs drop.

See examples/tree.br.

The optimizer

The compiler tidies the code it generates. A program must behave exactly the same with and without it, and --no-opt switches all of it off, which is the first thing to try when you suspect a compiler bug.

  • Constant folding: 2 * 3 + 1 becomes 7 and 1.5 + 2.25 becomes 3.75 at compile time, with the same wrapping integers and IEEE floats the running program would use. A division by a constant zero is left alone, so it still stops the program.
  • No temporaries for simple operands: in n - 1 or sum + i a literal or a local variable is used directly instead of being stored and loaded again.
  • Conditions jump on the flags: if, while, and, or and not compare and branch without first making a true/false number. Comparisons with NaN behave as before.
  • Cleanups: a value loaded right after it was stored, jumps to the next line, and code that can never run are removed. Functions with an asm block are left exactly as written.
  • Cheaper entry: a function that holds only numbers and booleans no longer clears its local slots when it starts.

Variables in registers: the integer, boolean and pointer variables a function uses most, especially inside loops (and the counter of a for a..b loop), are kept in processor registers instead of memory, up to five per function. Floats, text, lists, records, variables whose address is taken and functions with asm, defer, spawn or await keep every variable in memory. A loop that adds to a variable 100 million times runs about three times faster, and recursive code such as fib close to twice as fast.

Inlining: a call to a small function is compiled in place, with no call, when the function is just return and an expression of a few operations, takes at most four numbers, booleans or pointers and returns one. func square(x: int) -> int return x * x end is inlined; a function with several statements, text, lists or records, a method, a generic, async, extern or recursive function, or one with asm, try, match or a lambda is still called. Arguments are evaluated once, in order, exactly as in a call, and the body only sees its own parameters and the names of its own module. The function itself is still compiled, so you can keep using it as a value. A loop that calls three small helpers 100 million times runs about 2.5 times faster.

Compile-time code generation

A program that uses comptime func, #[derive], #[generated] or a block form (see the syntax guide) is compiled in rounds. Each round finds every request in the program, builds one program for this machine that contains the generators and what they call, runs it as a child process, and splices the text it printed into the program; text that asks for more generation takes another round, up to eight.

  1. The generators are checked against the comptime subset by following the call graph.
  2. The compiler describes each type a generator will receive (name, kind, fields, variants, attributes and every type reachable from it) and writes a small driver: it rebuilds those descriptions, calls each generator and prints ok or fail records. The description is also written in a line-oriented text form, which is what the cache hashes.
  3. The driver is built for the host with the compiler's own back end (the PE writer on Windows, the ELF writer on Linux, so no Visual Studio or linker) and started with no input, a time limit, an output limit and a memory limit (a job object on Windows, setrlimit on Linux).
  4. The text is parsed into the program. Errors in it are reported at the use site with the generator's name and the generated line.

The generators run on the machine that builds, so --target linux on Windows runs a Windows program to generate code for a Linux executable. The cache lives in zila-comptime in the system temporary directory (the ZILA_COMPTIME_CACHE environment variable names another place) and holds one file per generator call, named by the SHA-256 of the compiler version, the host and target, the source of every function the generator reaches and the serialized input. Only successful results are stored; a damaged entry counts as a miss. Options: --comptime-timeout seconds (default 5), --no-comptime-cache and --comptime-dump.

There is no interpreter: compile-time code is native code, which is why the limit is a time limit. Programs and packages are found as before (the standard library, and the file itself); the files next to the source file that a use names are read too, so a program can keep its generators in a package of its own.

Linux

zila-parse prog.br --target linux -o prog writes an x86-64 ELF executable. The compiler does everything itself (its own assembler, no linker, no Visual Studio) and the program talks to the kernel with system calls. A program that does not call C needs no library at all (a static executable); one that declares extern functions is dynamically linked and starts through /lib64/ld-linux-x86-64.so.2. --asm --target linux prints the assembly instead. The result was checked under WSL with Ubuntu (glibc).

The language is the same and so is the output. A program whose main returns an error prints error: ... and exits with status 1, an abort writes abort: file.br:line: ... to standard error and exits with 101, and an integer division by zero is an abort (abort: main.br:7: division by zero) on both targets. Objects are reference counted as on Windows and live_objects() counts them. Small objects come from a 256 MiB region that the executable asks the kernel for, and large ones from mmap, given back when freed (this is the default allocator; #[allocator] replaces it); running out of memory is abort: out of memory (no file and line: the allocator has none).

The libraries have the same functions on both targets. Where a library talks to the operating system, a file called std/<name>.linux.br replaces std/<name>.br when you build for Linux (the Linux layers use epoll, pread/pwrite, sockets and a DNS client written in Zila Lang), so one source builds for both.

Windows and controls on both systems

use ui is one library with one way of programming: Window, TextBox, Button, ListView, Label, vstack, hstack, the properties text, count and selected, add, remove, clear, onClick, onChange, onSelect, layout, show, close, run and alert do the same on Windows and on Linux, and examples/ui.br builds for both without a change. Setting text runs onChange once, and only when the text really changed. A control keeps answering with what it held after its window is closed.

On Linux the library speaks the X11 protocol itself, over the X server's Unix socket: there is no C library, GTK or Xlib, so the program is still a static executable. It works with any X server, including XWayland and WSLg (DISPLAY picks the display; only local displays are supported). X11 has no controls, so the library draws text boxes, buttons, lists and labels with the server's built-in fixed font and handles the keyboard (typing, Backspace, Delete, arrows, Home, End, Tab, Enter) and the mouse (clicks, list selection, the wheel) itself. The layout rules, padding and sizes are the ones Windows uses; only the look differs. When no display can be reached the program stops with error: ui: cannot open a display: ....

For tests, the environment variable ZILA_UI_SCRIPT can name a file of input steps, one per line: click N (the Nth button), type TEXT, key backspace|enter|up|down, select N and close. ui.run() applies them to the first window and then closes it; alert does not wait while a script is active.

Changed in this version: the handle of a control is now id (it was hwnd, which never was part of the documented API), and use ws is rejected: ws is internal to net, so use net.

Differences to keep in mind: the wording of an operating-system error (the text after the path) is the platform's own; a program that prints times, ports or addresses prints what the machine gives.

Not supported yet

These parse, but the native compiler stops with a clear message when it meets them:

  • Fixed-size arrays.
  • Generic enums and type aliases, generic methods with their own type parameters, explicit type arguments at call sites (first<int>(x)), and interfaces as the type of a variable or parameter (they only work as bounds).
  • Spreading a list into arguments (f(...xs)).
