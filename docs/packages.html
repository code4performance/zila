Packages

A program can use libraries other people wrote. A library is a git repository of .br files; a project lists the ones it needs in brasa.toml, and the tool downloads them once into a cache. There is no registry: the address of a repository is its name. Building never uses the network.

In practice

brasa-parse --init myapp                                   # writes brasa.toml
brasa-parse --add https://github.com/someone/codec@1.2.0   # adds, downloads, writes brasa.lock
brasa-parse main.br -o main.exe                            # builds from the cache, offline

and in main.br:

package main

use codec

func main()
    print(codec.version())
end

Commit brasa.toml and brasa.lock. Anyone who clones the project and runs brasa-parse --fetch gets the same sources, checked byte by byte.

The manifest

[package]
name = "myapp"
version = "0.1.0"

[dependencies.codec]
git = "https://github.com/someone/codec"
version = "1.2.0"

brasa.toml is written in a small, strict subset of TOML: tables, key = "string" lines and comments. Arrays, inline tables and multi-line strings are rejected with the line number and the name of the construct. The table name after dependencies. is the name you write after use. version is a minimum. Unknown keys are errors.

[package] may hold an edition. It is stored and ignored for now: no edition exists before version 1.0, and 1.0 will use it to let a package choose the rules of the language it was written for. --init leaves it out.

Versions

A version is MAJOR.MINOR.PATCH and the tags of the repository are vMAJOR.MINOR.PATCH. The tool picks versions by minimal version selection: for each package, the highest of the minimums that your manifest and the manifests of the packages you use ask for. It never picks a newer version just because one exists, and it has no solver, so you can work the result out by hand and adding a package never upgrades another. --update is what raises a minimum, to the newest tag of the same major.

A different major version is a different package. Version 2 and up ends its module path with /v2 (the same repository, tags v2.*) and gets its own import name, so both can be used, even by different dependencies, and their types are different types:

brasa-parse --add https://github.com/someone/codec@1.2.0
brasa-parse --add https://github.com/someone/codec/v2@2.0.0     # named codec_v2

A package whose manifest asks for another major than yours is compiled against its own: two packages can each use codec and mean different ones, without clashing. Major 0 is one package like any other.

The lock file and the cache

brasa.lock is written by the tool. For every package in the final selection it records the version, the full 40-character commit the tag points to and a sha256: hash of the files. Fetched sources go to ~/.brasa (%USERPROFILE%\.brasa on Windows, or the directory named by BRASA_HOME), one directory per package version and commit, shared by all your projects and written atomically.

Every build recomputes the hash of each package in the cache and compares it with the lock. A changed file stops the build and says what was expected and what was found; a manifest the lock does not cover says brasa.lock is out of date; a missing cache entry says package 'X' is not in the cache; run brasa-parse --fetch. If a tag is later moved to another commit, --fetch reports it and leaves the lock alone; --update accepts it.

Commands

--init [name]
Writes brasa.toml.
--add git-url[@version] [--as name]
Adds the dependency and fetches. Without a version, the newest tag of the highest major that matches the URL. The name defaults to the last part of the URL (codec_v2 for /v2).
--fetch
Resolves the graph, downloads what the cache lacks, verifies, writes the lock.
--tidy
Removes dependencies no source file uses and trims the lock. No network.
--update [name]
Raises minimums to the newest tag of the same major, then fetches.
--offline
Never contacts a remote; a command that needs to fails and names what is missing.

They act on the project that holds the current directory (the nearest brasa.toml upward) and need no source file.

What a package can do

A matching hash proves that you got the code that was locked, not that the code is harmless. So the tool also tells you what each package contains that can break memory safety or reach outside the language: an unsafe block, an extern declaration (with the libraries it names) or an asm block. These are a package's effects; a package with none is written none.

--add, --fetch and --update print the effects of every package they download or whose version changed, and --update marks a package that gained one:

locked 1 package(s)
  example.org/codec@1.1.0: effects: unsafe  [CHANGED: was none, gained unsafe]

brasa-parse file.br --explain-link shows the effects of the code your program actually reaches next to the size of each package. To refuse an effect, add a policy to brasa.toml:

[policy]
forbid = "asm"

The value is one of "unsafe", "extern" or "asm" (one value; the manifest has no lists). A build then fails when any dependency, direct or indirect, has that effect, naming the package and the file. Your own code is not checked.

Git

Only the commands that download (--add, --fetch, --update) run git, found on your PATH, with fixed arguments and no shell, and with password prompts turned off (ssh agents and credential helpers work as you configured them). URLs may be https://, ssh://, git@host:path or file://. If git is missing the tool says git was not found on PATH. It is used only to download dependencies. Building from a populated cache needs neither git nor a network, and the compiler needs no other external tool: brasa-parse writes executables itself.

How use finds a package

For use a.b.c the first name is looked up among the standard library, the project's dependencies and its local packages (a directory a/ next to brasa.toml). A name can be in only one place and the standard names are reserved: --add and the manifest refuse them. The remaining names are directories inside the package, and the name you write in code is the last one:

use codec.stream        // the directory stream/ of the dependency codec
...
stream.next()

A package is the .br files directly in its directory, merged into one module: they see each other's names, a name declared twice is an error that names both files, and each file's package line must be the package's name (the directory name; for a dependency, its name in [package]). Files ending in _test.br are left out of builds; brasa-parse --test dir/name_test.br runs their #[test] functions together with the package's own files. A dependency's own uses are looked up with its manifest, not yours.

A name found nowhere is an error: unknown package 'x' (not in the standard library, brasa.toml or the project directory); to add one: brasa-parse --add <git-url>. A program with no brasa.toml still sees the standard library and the name.br files next to it, as before.

Across a package boundary only pub items are visible; see visibility.

What goes into the executable

Every package a program names with use, from the standard library or from a dependency, is compiled together with the program into one executable. Nothing is loaded when it runs: the program does not read .br files, the cache, brasa.toml or brasa.lock, and there are no shared libraries of Brasa code. The only thing the operating system links at run time is C code that the program declares with extern.

Only what the program can reach is kept. A function, global or string that nothing reachable refers to is left out, and a package's start-up code runs only when it does something the program can observe or sets a global that kept code reads. So use json without calling it adds no bytes, and a program that never opens a window does not import the window system. brasa-parse --no-prune turns this off, and brasa-parse file.br --explain-link shows how many bytes of code and data each package adds to the program.
