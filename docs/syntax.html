Packages & imports

Every file starts with a package declaration, followed by zero or more use declarations naming modules the file depends on.

package main

use text, list

A name after use is a standard library module, a dependency listed in zila.toml or a directory of .zila files next to it; a name that is none of them is a compile error. Packages explains the rest.

Types

A type declaration introduces a record (a struct), an enum (a fixed set of names, optionally carrying data), or a structural interface. Any type can be made generic with <T>, and appending ? to a type makes it optional (T?).

Basic types

Everyday code uses int, long, float, byte, bool, char and text (see Text and characters). int is another name for i32 (32-bit), long for i64 (64-bit) and float for f64: they are the same types, interchangeable everywhere, and error messages print the everyday names. Other sized integers such as u16, u64 or usize exist for low-level and C code. An integer literal is an int unless the context asks for another type, and a literal that does not fit (such as 3000000000) is an error that asks for a long. A conversion keeps every value, so an int goes into a long (and a u32 into an i64) without writing anything and int + long is a long; going the other way, between signed and unsigned of the same size, or between integer and float needs int(x), long(x), float(x) and so on. Arithmetic happens in the type of its operands and wraps there, so int * int wraps at 32 bits even when the result is stored in a long; write long(a) * long(b) for the exact product. Lengths and list indices are int, which limits a list, map or text to 2,147,483,647 elements (2 GB of text); the program stops with an error past that. Sizes and offsets of files and times are long. Lists are written []T, raw pointers *T, and a type followed by ? may be nil. float is a 64-bit number with a fractional part (see Floats).

Records

type Customer = record
    id: i32
    name: text
    email: text?
end

Enums with data

An enum variant can carry values. match over an enum must cover every variant unless it has a _ arm.

type Shape = enum
    Circle(float)
    Rect(float, float)
    Empty
end

Plain enums

type Color = enum
    Red, Green, Blue
end

Interfaces

Interfaces are structural (Go-style): a type satisfies an interface simply by having methods with matching signatures — there's no explicit implements clause and no inheritance. In Zila Lang an interface is used as a bound on a type parameter; see Generics.

type Printable = interface
    func to_text(self) -> text
end

Generics

Type parameters go in angle brackets after the type or function name, optionally bounded by an interface (T: Printable). Generics are monomorphized at compile time. The full rules are in the Generics section below.

type Stack<T> = record
    items: []T
end

func first<T>(items: []T) -> T
    return items[0]
end

func show<T: Printable>(x: T)
    print(x.to_text())
end

Function types & type aliases

type Handler = func(Request) -> Response or error
type Middleware = func(Request, next: Handler) -> Response or error
type Table = Map<text, List<i32>>

Functions & generics

Functions are declared with func. A parameter marked ref is a passing mode: the callee borrows the caller's value for the duration of the call (there's no borrow checker, so the compiler enforces the escape rule below); without ref, records, lists and maps are values: the callee gets its own, and writing to a list the caller still holds copies it first (cheap to pass, one copy on the first write). A function that fills the caller's list declares ref xs: []int and the call writes fill(ref xs); migrating older code means adding ref at both places or returning the new list. Parameters can have default values, and a trailing ...name: T parameter collects a variadic argument list.

Methods (receivers)

A function with a receiver in parentheses before its name becomes a method on that type. There's no class hierarchy — just functions attached to a type.

func (c: Customer) greet() -> text
    return "Hello, {c.name}"
end

func (ref s: Server) use(m: Middleware)
    s.chain.add(m)
end

ref parameters, defaults, and varargs

func fill(ref buf: Buffer, n: i32 = 4)
    buf.n = n
end

func log(msg: text, args: ...any)
    print(msg)
end

func main()
    var b = Buffer{}
    fill(ref b)
    fill(ref b, n: 8)
    let xs = [1, 2, 3]
    log("x", ...xs)
end

A ref is only a temporary borrow, not a type. Outside unsafe the compiler rejects storing it in a field, list, map or global, returning it, assigning it to another variable, passing it without ref, taking & of it, capturing it in a lambda, or sending it to spawn or an async function. Reading and writing its fields and elements, calling methods, iterating it and passing it on as ref r are fine. Use new T for a value that must live longer.

At the call site, ref is repeated before the argument (fill(ref b)) so by-reference passing is visible wherever it happens, not just in the declaration. A leading ... on an argument spreads a list into a variadic parameter.

Variables: let vs var

let declares an immutable binding; var declares a mutable one. Both can have an explicit type annotation or infer one from the initializer.

let VERSION = "1.0"
var counter: i32 = 0

Control flow

if and match are expressions — they produce a value when used as one, and behave as statements otherwise.

if / else if / else

var total = 0
while total < 10
    total += 1
    if total == 5
        continue
    else if total == 8
        break
    else
        print("n={total}")
    end
end

match

Patterns can combine alternatives with |; a bare _ matches anything. A match over an enum must be exhaustive unless it has a _ arm.

func area(s: Shape) -> float
    match s
        Circle(r)  -> return 3.14159 * r * r
        Rect(w, h) -> return w * h
        Empty      -> return 0.0
    end
end

func classify(n: i32) -> text
    match n
        0 -> return "zero"
        1 | 2 | 3 ->
            let s = "small"
            return s
        -1 -> return "minus one"
        _ -> return "many"
    end
end

A multi-line arm body (like the 1 | 2 | 3 arm above) runs until the next pattern -> or end.

for and while

for i in 1..5
    print("{i}")
end

let xs = [1, 2, 3]
for i, v in xs
    print("{i}: {v}")
end

Error handling

Zila Lang has no exceptions. A function that can fail ends its signature with or error (-> Config or error), or just -> error when it returns nothing. Inside it, writing try in front of a call hands a failure straight to the caller. error("message") creates an error; match reads a result with ok(value) and err(e), and call() ?? fallback supplies a default. Integer arithmetic never fails: +, - and * wrap at the width of the type, and MIN / -1 is MIN; math.checked_add, checked_sub, checked_mul and checked_div return int or error (kind Overflow, or InvalidInput for a zero divisor) when you need to know. A failure the caller can handle is a value: xs.get(i) gives the element or nothing, m.get(key, default) a default. For a mistake in the program itself (not bad input), abort("message") writes abort: file.zila:line: message to standard error and ends the process with exit code 101. An out-of-bounds index, an integer division or remainder by zero, a missing map key with m[key], take on an empty list, int(x) of a float that does not fit, a failed assert outside --test and running out of memory abort the same way. An abort cannot be caught and runs no defer, no drop and no unwinding, and buffered writers are not flushed. defer schedules an expression to run when the enclosing function returns — commonly used to release a resource right after acquiring it.

func load(path: text) -> Config or error
    let raw = try file.read(path)
    let f = try file.open(path)
    defer f.close()
    return try json.parse(Config, raw)
end

Kinds, messages and causes

An error carries three things: e.kind (an ErrorKind, what went wrong in a form a program can test), e.message (text for people) and e.cause (an error?, nil for a root error). error("message") has the kind errors.Other; error(kind, "message") picks one, and error(kind, "message", cause) also records what it was caused by. e.context("message") returns a new error with the kind of e and e as its cause, so a caller can say what it was doing without losing the reason; e.is(kind) is true when the error or any cause has that kind, and e.full_message joins the messages, outermost first, with : . try converts and wraps nothing: the kind, message and cause arrive exactly as they left. A function that returns an error as a value (a helper that builds errors) is written -> error?, because plain -> error means "fails or does not".

use errors

let Corrupt: ErrorKind = errors.kind("config.Corrupt") ?? errors.Other

async func read_config(path: text) -> text or error
    match await fs.read(path)
        ok(t) -> return t
        err(e) -> return e.context("reading {path}")
    end
end

func main()
    match await read_config("app.cfg")
        ok(t) -> print(t)
        err(e) ->
            if e.kind == errors.NotFound
                print("no config, using defaults")
            else
                print("failed: {e.full_message}")
            end
    end
end

Kinds are open: they are names of the form package.Name, equal when the names are equal, so any library can add its own with errors.kind("mylib.Corrupt") (do it once, at package level; the std namespace is reserved for the standard library). Because the set of kinds is open, a match over them could never be exhaustive: test with if e.kind == ... and e.is(...). A text is never a kind: error("NotFound", "x") is a compile error, and e.kind.name gives the name as text. The standard kinds and the kinds each library returns are listed under errors in the library.

Optional values (T?) use the same idea for "maybe missing" rather than "maybe failed": ?? supplies a fallback, and ?. safely accesses a field only when the value isn't nil.

func main() -> error
    let email: text? = c.email
    let e = email ?? "no email"
    let n = email?.len

    if email == nil
        return
    end
end

Reserved words

These words belong to the language and cannot be used as names.

Declarations
package use type record enum interface func return var let extern embed pub end comptime (see Compile-time code generation)
Control flow
if else match for in while break continue defer try
Tasks
spawn starts a task (see Tasks); async and await work with futures (see Async). spawn_thread starts an operating-system thread and shared makes a value that threads may read (see Threads).
Operators written as words
and or not for logic; bitand bitor bitxor bitnot for bits.
Values and low level

new T{ ... } makes a shared, reference-counted object of type Rc<T> (it needs a record literal; see shared objects and weak references); Weak<T>, weak(x) and upgrade() break reference cycles. A method or field may be named like a keyword after a dot (app.use(x)).

Visibility: pub

Every function, type, let / var, method and record field is private to its package unless it is written with pub. All the files of one package see each other's names; another package sees only the pub ones, and only as package.name. pub comes after attributes and before async, func, type, let, var and extern, and before a field name. A pub enum exports all its variants. Using a private name from another package is a compile error that says it is private.

package geo

pub type Point = record
    pub x: int
    pub y: int
end

pub type Counter = record
    n: int
end

// a record with a private field is built by a function of its own package
pub func new_counter() -> Counter
    return Counter { n: 0 }
end

A record literal (or new) of another package's type is allowed only when every field is pub (geo.Point { x: 1, y: 2 }); otherwise use a constructor function. Copying, passing and storing a whole value is always allowed. A pub declaration may not name a private type of its own package in its signature. A generic function keeps the access rights of the package that wrote it. A type satisfies an interface of another package only through pub methods. main, test_ functions, #[export] functions and the calls the compiler inserts need no pub.

Generics and interfaces

A generic function or record is written once with type parameters. The compiler makes one copy for each combination of types you actually use (monomorphization), so generic code is as fast as hand-written code and its size grows with the number of distinct instances.

func first<T>(items: []T) -> T
    return items[0]
end

type Stack<T> = record
    items: []T
end

func (s: Stack<T>) push(x: T)
    s.items.add(x)
end

let n = first([1, 2, 3])                     // T is int
let s: Stack<text> = Stack { items: [] }    // the expected type gives T
s.push("hello")
  • Type arguments are inferred from the arguments of a call and, when a parameter appears only in the result, from the expected type (let xs: []int = empty()). There is no first<int>(x) form. A call that leaves a parameter open, or gives one parameter two different types, is a compile error naming it.
  • Records: Stack<int> and Stack<text> are different types. A record literal needs the expected type to know its arguments. Methods of a generic record are written with the receiver Stack<T>.
  • Interfaces list methods, and a type satisfies one when it has a method of each name with the same parameter and result types. func (n: int) to_text() -> text gives built-in types methods too.
  • Bounds: func show<T: Printable>(x: T) accepts only types that satisfy Printable, and inside the function x.to_text() is allowed. Otherwise the error names the type, the interface and the missing or mismatching method.
  • Checked once, at the definition. A generic body is checked with T as an unknown type that only has its bound's methods, so calling x.to_text() without a bound, or writing a + b on two T values, is an error where the function is written, even if it is never called. Putting a T in text with "{x}" is checked per instance.
  • Self in an interface method signature means the type that satisfies the interface: func bigger(self, other: Self) -> bool is satisfied by func (a: Square) bigger(b: Square) -> bool. Anywhere else Self is an error.
  • Standard interfaces: Eq, Ord and Hash need no use; see Eq, Ord and Hash.
  • Interfaces are only bounds. func show(x: Printable) is an error (it would need dynamic dispatch); write func show<T: Printable>(x: T).
  • Not supported yet: generic enums and type aliases, async generic functions, methods with their own type parameters, and interfaces with type parameters. They stop with a message naming the form.

Eq, Ord and Hash

Three interfaces are available in every program without use: Eq (func eq(self, other: Self) -> bool), Ord (func compare(self, other: Self) -> int, negative, zero or positive) and Hash (func hash(self) -> long). A bound of Ord or Hash also provides eq, so one bound is enough. A declaration with one of these names in your package shadows the standard one.

type Version = record
    major: int
    minor: int
end

func largest<T: Ord>(a: T, b: T) -> T
    if a > b
        return a
    end
    return b
end

let v = largest(Version { major: 1, minor: 9 }, Version { major: 2, minor: 0 })   // 2.0
let names: Map<Version, text> = {}                                            // a record as a key
  • Derived for records and enums. eq is true when all fields are equal, compare compares fields in declaration order and returns the first non-zero result, and hash combines the hashes of all fields, so equal values hash alike. An enum compares its variants in declaration order (Dot < Circle(1)), then the payload. The derived methods are ordinary methods (a.compare(b) works) and recursive types work. A type that holds a field without the capability does not have it either, and the error explains the chain (Line is not Hash because field from: Point is not Hash because field x: float is not Hash).
  • Overriding. A method named eq, compare or hash with the interface's signature replaces the derived one everywhere: operators, maps, sets, sorted collections and generic code. A type that defines eq but not hash is not Hash, so it cannot silently become an inconsistent key; write both. A method with the wrong signature is an error naming the interface.
  • Operators. ==, !=, <, <=, > and >= stay operators. On records, enums with data, lists and maps they call eq and compare; on a type parameter they are allowed when the bound provides them (Eq gives == and !=, Ord also the ordering operators). A type without the capability is a compile error naming the type, the operator and the reason. x == nil keeps its meaning.
  • Built-in types. Integers and bool (false before true) are Eq, Ord and Hash. Text compares by bytes (text.compare). A float is Eq and Ord but not Hash: == and < keep their IEEE meaning, while compare is a total order (NaN after every number and equal to itself, -0.0 equal to 0.0), so sorting with a NaN is deterministic. Lists compare element by element (lexicographic, a prefix first); T? is the reference type itself, and nil equals nil and comes before any value; a map is Eq and Hash (same keys with equal values, in any order) but never Ord.
  • Identity types. A #[shared] record (and later new T and shared T) is Eq and Hash by identity, unless it declares eq or hash, and is not Ord unless it declares compare.
  • Library. use derive adds derive.hash_combine(h, x), the function derived hashes fold fields with, for hand-written hash methods. list.sort and list.contains, set.Set and sorted.map() build on these interfaces (see the standard library).

Floats

float (the same as f64) is a 64-bit IEEE 754 number; f32 is the 32-bit form, mostly useful for storage and for calling C. A literal with a fraction or an exponent is a float: 1.5, 2e3, 0.25.

let radius = 2.5
let area = 3.14159 * radius * radius       // a float
let count = 4
let share = area / float(count)            // convert the int on purpose
print(int(area))                          // 19: cuts off the fraction
print(0.1 + 0.2)                          // 0.30000000000000004
print(1.0 / 0.0)                          // inf
  • No silent mixing. int and float (or f32 and f64) never meet in one operation, and let x: float = 3 is an error: write 3.0 or float(3). % is not defined for floats.
  • Conversions. float(n) turns an integer into a float. int(x) cuts the fraction off toward zero, and aborts with float out of range for NaN, infinities and numbers too big for an int. f32(x) and f64(x) change the width.
  • IEEE behavior. Dividing by zero does not stop the program: it gives inf, -inf or NaN. Every comparison with NaN is false, except !=.
  • Printing uses the shortest text that reads back as exactly the same number: 0.1, 3.0, 1e21, 1.5e-7. Numbers from 1e-4 up to 1e16 are written plainly; others use exponent form. NaN, inf, -inf and -0.0 print as shown.
  • Math library. use math gives math.sqrt, math.floor, math.ceil, math.trunc, math.round (halves away from zero), math.abs, math.min, math.max, math.pow(x, n) with a whole-number power, and math.fixed(x, digits), which writes a float with a fixed number of decimals (math.fixed(3.14159, 2) is 3.14).
  • Calling C. extern functions take and return f64 and f32 the way Windows x64 expects, in the XMM registers.
  • Not everywhere. Floats work in the native compiler. The bare-metal target rejects floats. A float cannot be a map key (a float is not Hash, because NaN is not equal to itself).

Maps

A Map<K, V> stores values under keys. The key type K is text or an integer type; the value type V can be anything the native compiler supports. A map is built with a literal, read and written with m[key], and a value like a list: assigning it to another name or passing it to a function does not copy it until one of them is written, and writing to a map that another holder still has copies it first (use ref to change the caller's map).

let ages = { "ada": 36, "alan": 41 }       // a Map<text, int>
var seen: Map<int, text> = {}              // an empty map needs its type

ages["grace"] = 45                       // adds a key (or replaces the value)
print(ages["ada"])                       // 36
print(ages.len)                           // 3
print(ages.has("alan"))                  // true
print(ages.get("linus", 0))              // 0: the default, because there is no such key
ages.remove("alan")                      // does nothing when the key is not there

for name, age in ages                     // keys and values, in insertion order
    print("{name} is {age}")
end
  • Types are inferred from the expected type or from the first pair of a literal, and every other pair must match them. {} has nothing to infer from, so it needs a type annotation, just like an empty list.
  • A missing key stops the program. m[key] on a key that was never stored aborts with map key not found, like an index out of bounds. Use has or get(key, default) when the key may be missing.
  • Methods: has(key), get(key, default), remove(key) and clear(). The number of entries is the property len, as for lists and text.
  • Iteration order is insertion order. for key, value in m and for key in m visit the keys in the order they were first added. Replacing a value keeps the key's place; removing a key and adding it again moves it to the end. Do not add or remove keys inside the loop.
  • Keys are any Hash type. Text, integers, bool, records and enums whose parts are Hash, lists and optionals of such types, and types held by reference (by identity, or by their own eq and hash) can be keys; two keys that are == are one key. A key that is not Hash is a compile error naming the type and the reason (a float field, an eq without a hash); see Eq, Ord and Hash. Do not change the hashed fields of a key held by reference after inserting it: lookups become unspecified (never memory-unsafe). Maps work in the native compiler, but not in the bare-metal target.

defer

defer call(...) runs a call when the function ends, however it ends: with return, by running off the end of the body, or because a try failed. It is how you make sure a file is closed or a lock released without repeating the cleanup before every exit.

func process(id: int) -> int or error
    print("start {id}")
    defer print("finished {id}")      // runs however the function ends

    if id < 0
        return error("negative id")
    end
    defer print("cleaning up {id}")   // runs first: last in, first out
    return id * 2
end
  • Last in, first out. Deferred calls run in the reverse order of the defer statements that were executed, before the function's local variables are released.
  • Function scope. A defer inside a loop or an if schedules one call each time it is executed, and all of them run when the function ends, not at the end of the loop. A defer that is never reached schedules nothing.
  • Captured when it runs. The variables a deferred call uses have the values they had when the defer statement ran (defer print("n = {n}") prints the old n even if it changes later). Records are shared, not copied, so defer c.report() sees the record as it is when the function ends. Because the values are captured, a deferred call cannot assign to a variable.
  • Only calls. defer needs a call; defer x + 1 is a compile error. If the call can fail (or error), its error is ignored and does not change what the function returns.
  • The return value is untouched, including a T or error result.
  • Where it does not run. Not on break or continue (they leave a loop, not the function), and not when the program aborts, as with an index out of bounds, a division by zero or a call to abort. Lambdas and async functions each have their own deferred calls.

Async

An async func starts as its own task when called and returns a Future<T>; await waits for a future without blocking the other tasks. await is allowed in any function, method, lambda or deferred call (it suspends only the current task), but not in a drop method or a function called from C, and it works with try on futures of T or error. Timers, files and TCP are covered on the Async page.

async func double(n: int) -> int
    await sleep(100)
    return n * 2
end

func main()
    let f = double(21)      // starts running now
    print(await f)           // 42
end

Text and characters

A text is an immutable sequence of bytes that holds UTF-8, and s.len is the number of bytes, not of characters: "ação".len is 6 because ç and ã take two bytes each. A char is one Unicode code point ('ç' is a char; so is '😀'). A char compares with ==, < and the other operators by code point, prints and interpolates as the one-character text, and is not an int: let n: int = 'a' is an error and c + 1 does not exist. Two conversions cross the line: c.code is the code point as an int, and char(n) makes a char from an integer (it aborts for a negative number, a number above 0x10FFFF or a surrogate, 0xD800 to 0xDFFF). A char also has c.to_text(), c.len_utf8() (1 to 4) and c.is_ascii().

let s = "ação"
print(s.len)                  // 6   (bytes)
print(s.char_count())         // 4   (characters, counted by walking the text)
for c in s
    print("{c} {c.code}")     // a 97, ç 231, ã 227, o 111
end
print(s.slice(0, 3))          // aç   (byte positions 0 up to 3)
print(char(231).to_text())    // ç

for c in s visits the characters in order. A byte that is not valid UTF-8 (possible only in text that came from outside the program, such as a file or a socket, which is not checked when it is read) is visited as U+FFFD, one per bad byte, and the loop never aborts. s.slice(a, b) takes byte positions and aborts, naming the position, when a or b is out of range, when a > b, or when a position falls inside a character: "ação".slice(0, 2) aborts with text position 2 is not on a character boundary. So a text built by the program is always valid UTF-8. s.bytes() returns a copy of the bytes as a []byte, s.byte(i) returns one byte in constant time without copying (and aborts out of range), and s.char_count() counts the characters (an invalid byte counts as one). text.from_bytes(b) in the text library turns bytes back into text and checks that they are valid UTF-8.

There is no s[i] on a text: "ação"[2] would be half of a character. The compiler says text cannot be indexed and points to s.bytes(), s.slice(a, b) and for c in s. In a loop that reads many bytes, use s.byte(i) rather than calling bytes() every time. There is no normalization, grapheme or locale support: a character is a code point, and upper and lower in the library change ASCII letters only. chr(n) is gone; write char(n).to_text(). See the unicode example.

String interpolation

Text literals can embed any expression inside { }, including nested calls and string literals. A literal brace is escaped as \{, and a literal quote as \".

let msg = "braces \{ and quote \" and {xs[0] + 1} and {fmt("a")}"

Attributes

Attributes (#[...]) attach metadata to the declaration that follows — they can stack, and some take arguments.

type User = record
    id: i32
    #[json("full_name")] name: text
    #[json(skip)] password: text
    email: text?
end

#[naked]
#[cfg("x86_64")]
func halt()
    asm
        cli
        hlt
    end
end

#[no_alloc] and #[allocator]

#[no_alloc] on a function is a promise the compiler checks: neither the function nor anything it calls may allocate. The allocating operations are a fixed list: text with interpolation, list, map and set literals (an empty [] too), Map.new() and the other collection constructors, new, a closure that captures a variable, spawn, channel, defer, c.alloc, calling an async function, and the list and text methods add, push and slice. Text without interpolation and a closure that captures nothing do not allocate. The standard library is analysed like your own code, so there is no list of allocating functions to keep. A function that calls through a function value (a parameter or a local holding a function) is rejected, because the callee is unknown. Calls on a type parameter bound by an interface are analysed as direct calls to every method of that name. extern functions are trusted unless marked #[allocates], and asm blocks are not looked into. The error names the chain: 'parse_line' is #[no_alloc] but allocates, then parse_line -> trim_all -> text interpolation at util.zila:12.

A program replaces the heap with three functions of fixed signatures, at most one of each. The runtime keeps the object headers, reference counts and zeroing; the allocator only hands out raw memory (it may return it uninitialized), and the runtime asks for the payload plus a 24-byte header, aligned to 16. They are checked as #[no_alloc] themselves, are accepted only in the program (not in std/), and need both alloc and free; realloc is optional and used to grow lists (without it the runtime allocates, copies and frees). A null from alloc or realloc ends the program with out of memory. live_objects() keeps counting; heap_bytes() is a compile error with a custom allocator.

#[allocator(alloc)]   func my_alloc(size: u64, align: u64) -> *u8
#[allocator(free)]    func my_free(ptr: *u8, size: u64, align: u64)
#[allocator(realloc)] func my_realloc(ptr: *u8, old: u64, size: u64, align: u64) -> *u8

See examples/no_alloc.zila and examples/allocator.zila.

Compile-time code generation

A comptime func runs while the program is being compiled. It receives a Type, a value that exists only at compile time and describes a declared type, and returns Zila Lang source text that the compiler compiles as if you had written it. Libraries use this to add per-type code (equality, JSON, printing) and their own block syntax without any change to the compiler.

use reflect

#[derive]
comptime func describe(t: Type) -> text
    var parts = ""
    for f in t.fields()
        parts = parts + " {f.name}=\{v.{f.name}\}"
    end
    return "func (v: {t.name()}) describe() -> text\n    return \"{t.name()}{parts}\"\nend\n"
end

#[derive(describe)]
type Point = record
    x: int
    y: int
end

// somewhere else: p.describe() gives "Point x=1 y=2"

The Type API

A Type answers name(), kind() (record, enum, alias, int, float, bool, text, list, map, set, optional, func), fields() for records (each with name, ty, attrs and line), variants() for enums (each with name, fields, attrs and line; a payload is written Circle(r: float), or is positional and called _0, _1), element(), key() and value() for containers, inner() for optionals and aliases, and attrs(). An attribute has a name and args, the arguments written in the source as text: #[json("full_name")] is json with the argument full_name. Sizes, offsets and alignment are never exposed, so the answers do not depend on the target. Type exists only in comptime code: using it anywhere else is a compile error. See reflect.

Derive, generated functions and blocks

  • #[derive(a, b)] on a type runs the #[derive] comptime funcs named a and b (found in the program's own package or an imported one; write json.json to choose between two) with the type. The text it returns is added to the program: methods (func (v: Point) describe()), helper functions, constants and types. An unknown or ambiguous name is an error at the attribute. A derive cannot change the declaration it is attached to, and a generated method that collides with an existing one is an error naming both.
  • #[generated(gen)] func parse(comptime t: Type, raw: text) -> t has no body. A call parse(Config, raw) (or parse<Config>(raw)) runs gen with Config; the text it returns is the body of a copy of parse for Config, in which t stands for Config. There is one copy, and one run of gen, per type. The argument must be a type name known at compile time; a variable is an error.
  • #[block] comptime func shout(raw: text) -> text gives the name shout a block syntax: a line that holds only that name (or ends with it, as in let s = shout), the raw lines, then a line that is only end. The raw text goes to the function unchanged and the source it returns replaces the block: an expression, or statements when the block stands alone on a line. The name must belong to an imported package or the file itself; a name that is not a block is an ordinary identifier. The formatter keeps the lines of a block as they are (it aligns only the name and end) and the language server never looks inside.

What a comptime function may do

Only text, lists, maps, sets, records, enums, loops and calls to code that does the same, and that includes every function it reaches. The compiler follows the calls and rejects extern functions, asm, unsafe, raw pointers, spawn, async, await, channels, global vars and anything that reaches files, sockets, the clock or the console, naming the chain: `async` is not allowed in comptime code: gen -> helper -> fs.read. text, list, format and math are fine; nothing is allowed or denied by library name. A comptime function cannot be called from runtime code.

Names, limits and errors

  • Hygiene. The top-level functions, types and constants a generator emits are renamed so that they cannot capture or collide with your names; methods attach to their type. Names that start with __ are reserved (a program that declares one is rejected). reflect.fresh("tmp") gives a local name that is unique in the build.
  • Limits. One run of generators may take 5 seconds (--comptime-timeout seconds), write 1 MiB per call and use 1 GiB of memory; output that itself asks for generation is expanded for at most 8 rounds. The limit is time rather than steps because the generators are compiled native code. Exceeding one, or a crash, is an error naming the generator and where it was used.
  • Errors point at your code. A generator refuses with reflect.fail("message", field) and the error is reported at that field's line with the generator's name. A mistake in generated text is reported at the #[derive], the call or the block, with error in code generated by `gen` for `Type`, the message and the generated line. --comptime-dump prints everything the generators produced to standard error.
  • Cross-compiling. Generators are built for, and run on, the machine that compiles, whatever --target says; reflect.target() tells them which target the build is for.
  • Trust. A generator is code that runs on your machine during the build. The subset check is what makes running a package's generators reasonably safe: it is enforced for every function a generator reaches, the process has no input, a time limit, an output limit and a memory limit, and the language server and the formatter never run one. It is not a hard sandbox against code that gets around the check; read the generators of packages you do not trust.

Results are cached on disk, keyed by a hash of the compiler version, the target, the source of what the generator reaches and the description of the type, so an unchanged build does not run the generators again (--no-comptime-cache turns this off). See the pipeline and examples/comptime.zila.

FFI & inline assembly

Calling a foreign function, dereferencing a raw pointer, and running inline assembly are all considered unsafe and must sit inside an unsafe block. extern declares a foreign function (ABI defaults to "C"); trailing ... declares a C-variadic parameter list.

#[link("m")]
extern "C" func sqrt(x: f64) -> f64

extern "C" func printf(fmt: *c.char, ...) -> c.int

#[export("zila_add")]
func add(a: i32, b: i32) -> i32
    return a + b
end

func main()
    unsafe
        printf(c.cstr("sqrt(2) = %f\n"), sqrt(2.0))
    end
end

Inline asm blocks hold assembly written as it is, one instruction per line with no quotes (labels, ; comments and memory operands like [rax] work as in any assembler, and so do instructions named like Zila Lang words, such as in al, dx). A line in/out/inout name = expr binds an operand (to a named register or an allocated one), an optional clobber line lists registers (clobber cc, memory), and the block ends at a line that is just end. Lines written as strings ("cli") are still accepted.

#[cfg("x86_64")]
func rdtsc() -> u64
    var lo: u32 = 0
    var hi: u32 = 0
    unsafe
        asm
            rdtsc
            out eax = lo
            out edx = hi
        end
    end
    return u64(hi) << 32 bitor u64(lo)
end

SQL is written the same way, in a sql block: sql postgres or sql tsql on a line, the statement as raw lines, and a line that is just end. The block is a value (db.Sql); a {value} in it becomes a bound parameter and is never pasted into the text. sql opens a block only when a dialect name and the end of the line follow, so a variable or parameter called sql still works. See Databases.

See the FFI & low-level example for a fuller walkthrough, and the project's docs/zila-ffi.md for the full specification (ABIs, #[c_layout], #[link]/#[link_src], #[cfg], and naked functions).

Testing

A test is a function marked #[test] that takes nothing and returns error (or nothing). assert(cond), assert(cond, "message") and assert_eq(a, b) (numbers, booleans, floats and text) end the test with an error that names the line when a check fails, the same way try ends a function, so they are only allowed in a function that returns error or T or error. A helper that checks things is written -> error and called with try.

#[test]
func clamp_keeps_values_inside() -> error
    assert_eq(clamp(5, 0, 10), 5)
    assert(clamp(99, 0, 10) <= 10, "above the range")
    return
end

Run them with zila --test file.zila (the file must be in package main). A failed check prints FAIL clamp_keeps_values_inside: line 7: assertion failed: left 3, right 4; a test that crashes the program stops the run of that file. examples/testing.zila is a complete example.

Note: Explicit generic arguments work at call sites (first<int>(x)) when written without spaces around the brackets; the rest are still inferred.
