## Context

Written in Brasa as standard libraries like `std/net.br` and `std/json.br`; the compiler only learns the library names. Existing: `net` (TCP, `Reader`), `tls` (client; SChannel on Windows, OpenSSL on Linux), `task` (cheap tasks, timers, no function coloring), `json` and `reflect` (comptime reflection: `parse(T, s)`, `#[generated]` functions, attributes with literal arguments), interfaces, `bufio`. Missing: any hash or random source, `tls` upgrade of an open connection, ALPN, a way to trust a private CA for one connection.

The specs carry the behavior; this document records the choices the specs do not show. `examples/rest_api.br` sets the surface style.

## Goals / Non-Goals

**Goals:**
- A short program queries PostgreSQL or SQL Server into records, with the same code on both.
- Pure Brasa over `net`/`tls`; no C driver is linked. Windows and Linux behave the same.
- Secrets never appear in errors or logs; TLS is the default.
- Real servers are one command away for contributors, and never required to run the suite.

**Non-Goals:** the proposal's non-goals.

## Decisions

1. **`db.Conn` is a record of functions, not an interface.** Checked against the compiler while implementing: an interface can only bound a type parameter (it cannot be the type of a value), a `#[generated]` function cannot be a method and a method cannot have its own type parameters, and a variadic parameter has one type. So: `Conn` is a record whose fields are the driver's functions (`run(sql, args: []Arg) -> Rows or error`, `begin_tx`, `commit_tx`, `rollback_tx`, `close_conn`) plus shared state, built by the driver with `db.connection(...)`; `exec`, `begin` and `close` are methods written once; `query` and `one` are `#[generated]` free functions, `db.query(T, conn, sql, args...)`, like `json.parse(T, s)`. `T` is decoded by generated code that maps columns to fields as `json` does (`#[db("x")]`, `#[db(skip)]`, optionals for `NULL`): a first generated function builds, once per result, the column index of each field (an error naming a field with no column), and a second reads each row. Parameters are `db.Arg` values (`Int`, `Float`, `Bool`, `Text`, `Bytes`, `Vector`, `Null`) made with `db.int`, `db.float`, `db.bool`, `db.str`, `db.bytes`, `db.vector`, `db.null()`; a bare `5` is a compile error naming `int`.
   - A transaction is a shared `Tx` that holds a `Conn` copy (`tx.conn`) tagged with the transaction's id; the shared state holds the id of the open transaction, and every statement checks that the connection's tag equals it, which gives the errors for "connection used during a transaction", "nested begin" and "transaction ended". A value being dropped cannot wait on the network (`await` is not allowed in `drop`), so a `Tx` dropped without an end only marks the state, and the connection sends `ROLLBACK` before its next statement.
2. **PostgreSQL driver.** Message framing (type byte, length, body) over a `net.Reader` or `tls.Conn`; startup, `SSLRequest` then `tls.upgrade`, auth (SCRAM-SHA-256 with server-signature check, md5, cleartext only on TLS), then per statement Parse (unnamed statement, parameter OIDs 0 so `$1` takes the type the SQL implies), Bind (text format), Describe, Execute, Sync, reading to `ReadyForQuery`. Text format because it is uniform and easy to decode into target types; binary is a later optimization. `[]float` goes as the text `[1.0,2.5]` with no cast (the server infers `vector` from the context, which is how pgvector is used); `?max_rows=N` in the URL sets the row limit (error kind `Overflow`). Transport errors (a reset, a closed socket) become `Unavailable` and mark the connection closed. The real-server tests do not need the Docker environment: `BRASA_TEST_POSTGRES` can name any server (they write only to TEMP tables, which vanish with the session), and the Docker environment stays an optional way to get servers. Transactions are `BEGIN`/`COMMIT`/`ROLLBACK` and the connection tracks the status byte of `ReadyForQuery`. MD5 login is kept because older servers use it, but PostgreSQL has deprecated it; if the 19 image no longer accepts it, its real-server test is dropped and the fake-server test remains.
3. **SQL Server driver and encryption.** TDS packets (8-byte header, default size 4096), `PRELOGIN`, `LOGIN7` (the password obfuscation is not encryption, hence the encryption modes), token streams (`COLMETADATA`, `ROW`/`NBCROW`, `DONE*`, `ERROR`, `INFO`, `ENVCHANGE`, `RETURNSTATUS`, `RETURNVALUE`, `LOGINACK`). Parameters use an `RPC` to `sp_executesql` with typed parameters, plain statements `SQLBATCH`. TDS 7.x `on` wraps the TLS handshake in TDS packets, which `tls` cannot do without a transport hook; TDS 8.0 (`strict`) does TLS first, then TDS, which fits `tls.connect_with` and ALPN `tds/8.0`. So `strict` and `off` are supported and `on` is rejected with a clear message. Single-byte `varchar` is decoded as code page 1252, 1250 (Central European) or 1251 (Cyrillic), chosen by the collation's language, or, for a UTF-8 collation, as UTF-8; a non-ASCII value in a collation of any other code page (Greek, Turkish, Hebrew, Arabic, Baltic, East Asian, ...) is an error that points at `nvarchar`. `xml` is read as text (a PLP of UTF-16). A named instance on this machine is reached through its named pipe (`fs.pipe`, an overlapped duplex client in the `fs` library that shares the scheduler's completion port; a stub returning `Unsupported` on Linux) and any other instance through the TCP port the SQL Browser reports; this is what made a local instance with TCP disabled reachable. `nvarchar` is UTF-16 and exact. Checked while implementing: `encrypt=off` sends pre-login `ENCRYPT_NOT_SUP`, so nothing is encrypted and the login password is only obfuscated; a server that forces encryption answers `ENCRYPT_REQ` and the driver reports that `encrypt=strict` is needed. `strict` negotiates ALPN `tds/8.0` over TLS 1.3 against SQL Server 2025.
4. **`ca_file` instead of an "insecure" switch.** To test against Docker servers the client must trust a development CA. Adding trust anchors for one connection keeps the rule "validation cannot be turned off" and touches nothing system-wide. On Linux (OpenSSL) it is loading the file as extra verify locations next to the system ones; on Windows (SChannel) the handshake runs with manual credential validation and the library then builds the chain with the system roots and, when no trusted root is found, a second chain with an engine whose only root store is the CA file, always checking the SSL policy for the host name. Both were implemented and pass the same tests (ALPN needed the application-protocols buffer on the first call). Waiting calls follow the language as it is: `async func` and `await` at each wait point, as in `net` and `tls`. PostgreSQL uses the standard parameter name `sslrootcert`; SQL Server uses `cafile`.
5. **`crypto` is plain Brasa with published test vectors.** SHA-256, MD5, HMAC and PBKDF2 are short and fully specified. `crypto.equal` is constant time (used by SCRAM verification and later by MCP tokens). Randomness comes from the OS (`BCryptGenRandom`, `getrandom`) via `extern`, with no fallback. No ciphers or signatures: it is for protocol use and says so.
6. **Docker environment (`tests/docker/`).**
   - `compose.yml` with the services and health checks, ports on `127.0.0.1` (55432 PostgreSQL, 51433 plain SQL Server, 51434 strict SQL Server from a second instance of the same image with a different `mssql.conf`), named volumes, one `.env` file with development-only credentials.
   - **PostgreSQL 19 (checked in task 1.1, 2026-11-07):** `postgres:19` and `pgvector/pgvector:pg19` do not exist yet; the newest 19 tags are `19rc1` (and `19beta1` to `19beta4`). The environment uses `postgres:19rc1` (build arg `PG_TAG`, to move to `19` when it is published) and a `Dockerfile` that builds pgvector v0.8.7 from source with `postgresql-server-dev-19` from the PGDG repository the image already uses; it compiled and the extension files are installed. `pg_hba.conf` requires `scram-sha-256` over `hostssl`, with the server certificate and key from the generated CA.
   - **SQL Server 2025:** `mcr.microsoft.com/mssql/server:2025-latest` with `ACCEPT_EULA=Y`, `MSSQL_PID=Developer` and a strong SA password from `.env`. One instance has no forced encryption (plain port); the other forces encryption through `mssql.conf` (`network.forceencryption = 1`, `tlscert`, `tlskey`, `tlsprotocols`) with the CA-signed certificate. Microsoft's documentation does not show a separate "force strict" key for Linux; verified by experiment that the forced instance negotiates ALPN `tds/8.0` over TLS 1.3 (a strict client connects) and that clients without TLS cannot connect, which is what the tests need. `sqlcmd` ships in the image (`/opt/mssql-tools18/bin`), so a one-shot init service seeds both instances with it.
   - `gen-certs.sh` (run through Docker's `alpine/openssl` image on Windows, so no local OpenSSL is required) creates a development CA and the server certificates for `localhost` and `127.0.0.1` into `tests/docker/certs/` (git-ignored); `ca.pem` is what tests pass as `sslrootcert`/`cafile`.
   - Nothing in `cargo build` or `cargo test` starts Docker. The folder's `README.md` documents `up`, `down -v`, the variables and how to run the real-server tests.
7. **Tests without the world.** Each driver is tested against an in-process fake server written in Brasa inside the tests (fake PostgreSQL: startup, SCRAM, extended query; fake TDS: pre-login, login, token streams) and against recorded byte exchanges from the real Docker servers stored under `tests/data/`, so a run without Docker still checks the real framing. The real-server tests give the final confirmation.
8. **Registration.** Each library is a portable file added to the tables in `src/codegen_x64.rs` and rejected in the bare-metal build, except `crypto` (without `random`).
9. **Where it lives.** In `std/` for now, like `net` and `tls`, because the package manager is not built; the drivers are natural candidates to become packages later with the same API.

## Risks / Trade-offs

- **Fakes can agree with a wrong reading of a protocol.** → Recorded real exchanges and the Docker servers; constants written from the PostgreSQL protocol documentation and MS-TDS, cited in the file headers.
- **TDS is the largest and riskiest part.** → Scope cut to SQL login, `strict`/`off`, `sp_executesql` and a listed type set with an explicit error for the rest; task 4.1 is a spike against the real container before the rest is built, and the plan is re-checked after it.
- **`ca_file` and ALPN on SChannel.** ALPN needs the application-protocols buffer (Windows 8.1+) and the extra-root validation is custom work. → Done and tested on both targets against the `tests/docker` TLS servers (task 1.6); ALPN works on Windows 11.
- **Image tags, the pgvector build for PostgreSQL 19 and the SQL Server 2025 strict-encryption settings were not verified while planning.** → Task 1.1 checks them first and writes the confirmed tags and settings into this design; if PostgreSQL 19 images are not available, the environment uses the newest released major and the task says so.
- **SQL Server image size (about 1.5 GB) and memory (2 GB minimum).** → Documented in the environment README; the environment is optional and the suite does not need it.
- **Development credentials in the repository.** → Obviously development-only, bound to loopback, named as such, and not accepted by any library default.
