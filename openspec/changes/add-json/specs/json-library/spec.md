## Purpose

Lets programs read and write JSON, either as a dynamic tree or directly into and out of their own types, with precise errors and no code generated by the compiler for it.

## ADDED Requirements

### Requirement: Dynamic values
`use json` SHALL provide the enum `json.Value` with the cases `Null`, `Bool(bool)`, `Number(float, text)` (the value and its original literal), `Text(text)`, `List([]Value)` and `Object(Map<text, Value>)`. `json.parse_value(s)` SHALL return `Value or error` and accept exactly the grammar of RFC 8259 (no comments, no trailing commas, no leading zeros, no `NaN` or `inf`), with surrounding whitespace allowed. `json.stringify(v)` SHALL return compact text with no whitespace, or an error for a number that is `NaN` or infinite. Object keys SHALL keep their order of appearance in both directions. Stringifying an unchanged parsed number SHALL give its literal back, including integers beyond 2^53.

#### Scenario: Parse a tree
- **WHEN** a program parses `{"a": [1, true, null], "b": "x"}` and matches the result
- **THEN** it gets an `Object` with `a` as a `List` of a number `1`, `Bool(true)` and `Null`, and `b` as `Text("x")`

#### Scenario: Stringify
- **WHEN** a program stringifies the value parsed from `{ "a" : [ 1 , 2 ] }`
- **THEN** the result is `{"a":[1,2]}`

#### Scenario: Large integer survives
- **WHEN** a program parses `12345678901234567890` and stringifies it without changes
- **THEN** the result is `12345678901234567890`

#### Scenario: Strict grammar
- **WHEN** a program parses `[1,]`, `01`, `{'a':1}`, `[1 2]`, `NaN` and the empty text
- **THEN** each result is an error

### Requirement: Typed decode
`json.parse(T, s)` SHALL return `T or error`, where `T` is passed as a type argument, and SHALL build a value of `T` from the JSON text. The mapping SHALL be: a record from an object whose keys are its field names; an enum without payloads from a text holding a case name; an enum with payloads from an object with one key, the case name, whose value is the payload (a list for several payloads); `[]T` from a list; `Map<text, V>` from an object; an optional `T?` from `null` (becomes `nil`) or a value of `T`; integer types from integral numbers inside the range of the type; `float`, `f64` and `f32` from any number; `bool` from `true` or `false`; `text` from a string; `json.Value` from anything. Keys of the JSON object that are not fields of the record SHALL be ignored. A missing key SHALL leave an optional field `nil` and SHALL be an error for any other field. The derivation SHALL be implemented by the library through comptime reflection, so any type reflection can describe works, including generic instances and nested types, without registration.

#### Scenario: Record
- **WHEN** a program decodes `{"id": 7, "name": "Ana"}` as a record with `id: int` and `name: text`
- **THEN** it gets that record with `id` `7` and `name` `Ana`

#### Scenario: Nested lists and maps
- **WHEN** a program decodes `{"a": [1, 2], "b": []}` as `Map<text, []int>`
- **THEN** it gets a map with `a` holding `[1, 2]` and `b` holding an empty list

#### Scenario: Optional and missing
- **WHEN** a program decodes `{"id": 1}` and `{"id": 1, "email": null}` as a record with `id: int` and `email: text?`
- **THEN** both give `email == nil`

#### Scenario: Missing required key
- **WHEN** a program decodes `{"id": 1}` as a record with `id: int` and `name: text`
- **THEN** the result is an error whose message is `missing field "name" at $`

#### Scenario: Unknown keys ignored
- **WHEN** a program decodes `{"id": 1, "extra": [1, 2]}` as a record with only `id: int`
- **THEN** it gets the record with `id` `1`

#### Scenario: Enums
- **WHEN** a program decodes `"Red"` as an enum with the cases `Red` and `Green`, and `{"Circle": 2.5}` as an enum with the case `Circle(r: float)`
- **THEN** it gets `Red` and `Circle(2.5)`

#### Scenario: User type without registration
- **WHEN** a program declares a new record and decodes JSON into it without any other declaration
- **THEN** it compiles and decodes, and the compiler contains no code that mentions JSON

### Requirement: Typed encode
`json.encode(x)` SHALL return the compact JSON text of any value whose type decode supports, or an error for a non-finite float, with the inverse mapping: records as objects with fields in declaration order, optionals as `null` when `nil`, enums as above, maps in insertion order. Decoding the result of `encode` into the same type SHALL give a value equal to the original.

#### Scenario: Record out
- **WHEN** a program encodes a record with `id` `7` and `name` `Ana`
- **THEN** the result is `{"id":7,"name":"Ana"}`

#### Scenario: Round trip
- **WHEN** a program encodes a record holding a list, a map, an optional and a nested record, and decodes the text back
- **THEN** the decoded value equals the original

### Requirement: Field attributes
`#[json("key")]` on a record field SHALL use `key` as the JSON key in both directions. `#[json(skip)]` SHALL leave the field out of `encode` and ignore its key in `parse`, which leaves the field at its zero value (empty text, `0`, `false`, empty list, empty map, `nil`). Any other content in a `json` attribute SHALL be a compile error naming the field. Two fields of one record resolving to the same key SHALL be a compile error.

#### Scenario: Rename
- **WHEN** a program encodes the `User` of `examples/types.br` with `name` `Ana Lima`
- **THEN** the text contains `"full_name":"Ana Lima"` and no `"name"` key

#### Scenario: Skip
- **WHEN** a program encodes a `User` with a password and decodes `{"id": 1, "password": "x"}` into a `User`
- **THEN** the encoded text has no `password` key and the decoded user has an empty password

#### Scenario: Bad attribute
- **WHEN** a field carries `#[json(rename)]`
- **THEN** compilation fails and the message names the field

#### Scenario: Key clash
- **WHEN** two fields of one record both resolve to the key `id`
- **THEN** compilation fails and the message names both fields

### Requirement: Text
Strings SHALL be UTF-8. Decoding SHALL accept the escapes `\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t` and `\uXXXX`, joining a high and a low surrogate escape into one character. A lone surrogate escape or an unescaped control character below 0x20 SHALL be an error. Invalid UTF-8 bytes SHALL be an error. Encoding SHALL escape `"`, `\`, control characters (as `\b`, `\f`, `\n`, `\r`, `\t` or `\u00XX`) and write every other character as its UTF-8 bytes unchanged, including characters outside the Basic Multilingual Plane.

#### Scenario: Unicode escapes
- **WHEN** a program decodes `"café 😀"` as `text`
- **THEN** the result is the UTF-8 text `café 😀`

#### Scenario: Lone surrogate
- **WHEN** a program decodes `"\ud83d"` as `text`
- **THEN** the result is an error

#### Scenario: Encode escapes
- **WHEN** a program encodes a text holding a double quote, a newline and the character `é`
- **THEN** the result is a string whose quote is written `\"`, whose newline is written `\n`, and whose `é` keeps its UTF-8 bytes

### Requirement: Numbers
Decoding into an integer type SHALL fail for a literal that is not integral and for a value outside the type's range; a literal that is integral in value, like `1e2` or `5.0`, SHALL be accepted. Nothing SHALL wrap or round. Decoding into a float SHALL give the correctly rounded value. Encoding a float SHALL write the shortest decimal text that reads back as the same value (the digits of `std/float.br`), in the JSON number grammar; `NaN` and infinities SHALL make `encode` return an error. Integers SHALL be written in decimal with no fraction.

#### Scenario: Overflow
- **WHEN** a program decodes `300` as `u8` and `9223372036854775808` as `int`
- **THEN** both are errors that name the type and the path

#### Scenario: Integral float literal
- **WHEN** a program decodes `1e2` and `5.0` as `int`
- **THEN** the results are `100` and `5`

#### Scenario: Fraction into int
- **WHEN** a program decodes `1.5` as `int`
- **THEN** the result is an error

#### Scenario: Shortest float
- **WHEN** a program encodes the floats `0.1`, `1e21` and `100.0`
- **THEN** each result decodes back to the same bits, and `0.1` is written with exactly the digits `0.1`

#### Scenario: Not finite
- **WHEN** a program encodes `NaN`
- **THEN** the result is an error

### Requirement: Errors
Every failure SHALL be an error value of kind `InvalidInput`. A syntax error SHALL have a message of the form `<what> at line L, column C` (1-based, column counted in characters). A mismatch between the JSON and the target type SHALL have a message of the form `<what> at <path>` where the path starts at `$` and uses `.key` for object keys and `[n]` for list positions starting at 0, such as `expected text, found number at $.users[2].email`. The first error SHALL be reported; no partial value is returned. Parsing and encoding SHALL never stop the program.

#### Scenario: Syntax position
- **WHEN** a program parses the two lines `{"a": 1,` and `  x}`
- **THEN** the error kind is `InvalidInput` and the message ends with `line 2, column 3`

#### Scenario: Type path
- **WHEN** a program decodes `{"users": [{"email": "a"}, {"email": "b"}, {"email": 5}]}` into a record with a list `users` of records that have `email: text`
- **THEN** the message is `expected text, found number at $.users[2].email`

### Requirement: Duplicate keys and depth
Decoding into a record or `Map<text, V>` SHALL fail when an object holds the same key twice, with the message `duplicate key "k" at <path>`. `json.parse_value` SHALL keep the last value of a duplicated key and its position stays that of the first occurrence. Nesting deeper than 128 levels of lists and objects SHALL be an error in `parse_value`, `parse`, `stringify` and `encode`, so that no input can exhaust the stack.

#### Scenario: Duplicate into record
- **WHEN** a program decodes `{"id": 1, "id": 2}` as a record with `id: int`
- **THEN** the result is an error with the message `duplicate key "id" at $`

#### Scenario: Duplicate in a dynamic value
- **WHEN** a program parses `{"a": 1, "a": 2}` and stringifies it
- **THEN** the result is `{"a":2}`

#### Scenario: Depth limit
- **WHEN** a program parses 200 nested `[` followed by 200 `]`, and another with 128 of each
- **THEN** the first is an error naming the depth limit, and the second succeeds

### Requirement: Pretty printing
`json.stringify_with(v, opts)` and `json.encode_with(x, opts)` SHALL take an options record with `indent: int` (spaces per level, `0` meaning compact, the default). With `indent > 0` they SHALL put each list item and object member on its own line, write `": "` after keys, and write empty lists and objects as `[]` and `{}`. Lines SHALL be separated by `\n` on every target and carry no trailing spaces.

#### Scenario: Indented
- **WHEN** a program stringifies the value parsed from `{"a":[1,{}],"b":null}` with `indent` `2`
- **THEN** the lines are `{`, `  "a": [`, `    1,`, `    {}`, `  ],`, `  "b": null` and `}`, joined by `\n`

#### Scenario: Compact default
- **WHEN** a program calls `json.encode` without options
- **THEN** the result has no whitespace outside strings

### Requirement: Targets
`json` SHALL behave identically on the Windows and Linux targets and SHALL NOT depend on the operating system. Memory SHALL be released as for any other Brasa values: decoding and encoding in a loop SHALL keep the number of live objects flat.

#### Scenario: Same output on both targets
- **WHEN** the same program encodes and decodes a record on both targets
- **THEN** both print identical text

#### Scenario: No leaks
- **WHEN** a program decodes and encodes a record 1000 times and compares `live_objects()` before and after
- **THEN** the count is unchanged
