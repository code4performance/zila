## Context

The lexer (`src/lexer.rs`) drops comments and whitespace and its tokens (`Token { tok, line, col }`) carry parsed values (`Tok::Int(u64)`, text parts with escapes already resolved), so the original spelling cannot be rebuilt from a token. The parser knows exactly where blocks begin and end (about 17 places consume `end`), but the AST has no end positions or comments. Function *types* (`func(int) -> bool`) and `extern func` declarations contain the word `func` without opening a block, so indentation cannot be decided from keywords alone. The CLI (`src/cli.rs`) has a single list `FLAGS` that `tests/docs.rs` compares with the docs.

## Goals / Non-Goals

**Goals**
- A formatter that can never change a program and keeps every comment.
- Rules simple enough to explain in a paragraph, close to how the repository's own code is already written.

**Non-Goals**
- Reflowing long lines, reordering or aligning declarations, normalizing operator spacing (`a+b` stays `a+b`), configuration options, formatting inside text interpolations, an editor integration (a later tooling item).

## Decisions

1. **Work on source slices, not on the AST.** The lexer gets a variant `tokenize_all()` that returns, besides the tokens, the char offsets `start..end` of each token (a new `span` field on `Token`) and the comments (`Comment { start, end, text, line }`). The normal `tokenize()` is unchanged for everyone else. The formatter copies the original text of each token, so spellings and escapes are preserved by construction. (Text literals cannot span lines in Brasa. Tokens are compared ignoring the line and column recorded for interpolations, which move when a line is reindented.)
2. **Block structure from the parser.** The parser records pairs: `open_block()` is called where a construct that ends with `end` begins (func declaration and lambda with a body, `if`, `while`, `for`, `match`, `unsafe`, `asm`, `record`/`enum`/`interface` bodies), and each place that consumes `end` goes through `close_block()`, which pops the opener and records `(opener token index, end token index)`; `else` tokens (including `else if`) are recorded too. The recorder is a field of `Parser` read after parsing (`parse_with_layout`), so existing callers are unchanged. Nothing is guessed from keywords, which settles function types and `extern func`.
3. **Line layout.** The formatter walks the tokens line by line (`Newline` tokens separate lines). The indentation of a line is the number of blocks open at its first token, minus one if the line starts with `end` or `else` (the block level of an `else` line is that of its `if`), plus the continuation depth: one for each bracket opened and not yet closed on earlier lines, plus one when the previous line ended with a binary operator or `=` (`+ - * / % == != < <= >= << ?? = += ... & | and or bitand bitor bitxor ..`; not `>` or `>>`, which end generic types such as `Map<K, V>`, and not `^`, the postfix dereference) or the line starts with `.` or `?.` (a method chain). `case`: a line that starts with a closing bracket is dedented by one bracket.
4. **Within a line.** Tokens are joined with the spacing of the source (so columns aligned with spaces, as in `Circle(r)  -> ...`, stay aligned; tabs become spaces), then fixed: no space before `,` `)` `]`, none after `(` `[`, exactly one after `,`. Adjacent tokens never gain or lose a space otherwise, which is what makes the token-equality check hold. Text, character and number tokens are copied from their spans.
5. **Blank lines.** Blank runs are limited to one; they are removed after a line that opens a block (`func ...`, `if ...`, and so on, per the parser pairs) and before an `end`/`else` line, and at the start and end of the file.
6. **Comments.** A comment after code on the same line is appended after at least two spaces (the original gap when it is wider). A comment alone on its line is indented like the next line that holds a token (before an `else`, as the `else`; before an `end`, one level deeper than the `end`, so a closing comment stays inside its block). Block comments (`/* */`) keep their inside; their first line is positioned like a line comment. Comments between tokens of one line are kept where they are.
7. **`asm` blocks.** The lexer already reads their lines raw (`Tok::Text` tokens whose text is the trimmed line), so the formatter takes the original lines from the source, computes the smallest indentation among the non-blank ones and re-indents them to the level of `asm` plus one, keeping the relative indentation. Operand lines (`in x = ...`) and clobbers are ordinary tokens on lines inside the block and are indented to the same base.
8. **Safety net.** After formatting, the result is lexed again and its token kinds must equal the original's (positions ignored, comments compared as text and order), and the result with all whitespace removed must equal the original with all whitespace removed (so nothing but whitespace can differ, which also catches a lost comment). If not, the result is discarded with the error "formatting would change the program" (this never happens if the rules are right; it exists so that a formatter bug cannot damage a file). Idempotence is tested separately.
9. **Line endings.** The text is processed with `\n`, then converted to CRLF if the original used CRLF (the majority of line endings decides).
10. **CLI.** `--fmt` and `--fmt-check` are added to `FLAGS` and to `Mode`; every positional argument is a file. Output: `--fmt` prints `formatted <path>` for each changed file; `--fmt-check` prints `not formatted: <path>`. A parse error prints `<path>: <line>:<col>: <message>`.
11. **The repository.** After the formatter works, `brasa-parse --fmt` is run over `std/`, `examples/` and `os/` (the rules were chosen to match the existing style, so few lines should change), and `--docs` regenerates the example blocks of the documentation if examples changed.

## Risks / Trade-offs

- Continuation indentation is heuristic (brackets and trailing operators); statements that continue on the next line without either are not recognized and stay on one level (they are rare because the parser needs a bracket or an operator to continue).
- `match` arms with bodies on following lines depend on the parser's recorded blocks; the arm body is not a block with `end`, so an arm's body lines are indented one level more than the arm line when they are on separate lines. The tests cover both the one-line and the multi-line forms.
- Reformatting the repository touches many files; the token-equality check and the test suite guard it, and it is done in a separate step so it can be reviewed apart.
