## Context

Today `Map<K, V>` is a runtime object (`src/runtime_map.asm`): 32-byte entries `[state][hash][key][value]` plus an open index, a flags word (`1` text keys, `2` values are heap objects) and `rt_map_hash`, which hashes either a text (FNV-1a) or an integer (multiplicative mix); `rt_map_find` compares with `rt_text_eq` or integer equality. `map_type` in `src/codegen_x64.rs` rejects any key that is not `text`, an integer or a type parameter, with "keys are text or integers". `std/set.br` wraps a `Map<T, bool>`; `std/sorted.br` is an AVL tree in Brasa ordered by a stored `less` function. Generic bodies are checked once with opaque `Ty::Param` types (`binary_core` rejects any operator on them), then instantiated per type arguments. Interfaces are structural: a type satisfies one when it has methods of identical signatures.

## Goals / Non-Goals

**Goals**
- One vocabulary (`Eq`, `Ord`, `Hash`) that the compiler derives for plain data and users can override.
- Any `Hash` type can be a map or set key, any `Ord` type a sorted key and a `list.sort` element, with the fast paths for `text` and integers unchanged.
- Generic code can compare values of a bounded `T`.

**Non-Goals**
- Deriving `to_text` (separate concern), multiple bounds on one parameter (a bound `Ord` or `Hash` implies `Eq` instead), user-selectable hashers, randomized hashing (maps stay insertion-ordered and deterministic).
- Changing float arithmetic or IEEE comparison semantics of `==` and `<`.
- Ordering for maps or identity-compared types (not meaningful, see decision 5).

## Decisions

1. **The interfaces.** Declared in a built-in prelude (no `use`): `Eq { func eq(self, other: Self) -> bool }`, `Ord { func compare(self, other: Self) -> int }`, `Hash { func hash(self) -> long }`. `Self` is a new type name valid only inside an interface method signature; it means the satisfying type, and satisfaction compares signatures with `Self` replaced by it. `hash` returns the 64-bit `long` of `add-int-long-aliases`. A bound `Ord` implies `Eq` (the generic body may use `==`; for a type with no `eq` of its own it means `compare(...) == 0`) and a bound `Hash` implies `Eq`. This keeps the single-bound rule of the `interfaces` capability.
2. **Derivation, written in Brasa.** For a record the derived `eq` is the conjunction of `eq` on each field in declaration order; `compare` is lexicographic over fields in declaration order; `hash` folds each field's `hash` with `derive.hash_combine(h, x)` (a fixed 64-bit mix) starting from a per-type constant. For an enum, `eq` requires the same variant and equal payload, `compare` orders by variant declaration index and then lexicographically by payload, `hash` combines the variant index with the payload hashes. (Implementation note: reflection had not landed, so the compiler writes the same functions as Brasa source per type; see the notes in `tasks.md`.) These are comptime functions in `std/derive.br` (`derive_eq<T>`, `derive_compare<T>`, `derive_hash<T>`) that iterate over the fields or variants of `T` with the reflection of `add-comptime-reflection`; the compiler invokes them once per type, the first time `eq`, `compare` or `hash` is needed and no user method of that name exists. Each result is a normal method, so `a.eq(b)` works, and a derived method can be called from a user override (`derive.eq(a, b)`). If a field's type lacks the capability, the type lacks it too, and the error explains the chain ("`Line` is not Hash: field `from: Point` is not Hash: field `x: float` is not Hash").
3. **Overriding and consistency.** A user method named `eq`, `compare` or `hash` with the interface's signature replaces the derived one. If the user defines `eq` but not `hash`, `hash` is not derived (a derived hash of the fields could break "equal values have equal hashes"), so the type is `Eq` but not `Hash`, and the key error says "defines eq but not hash". A user `compare` does not change a derived `eq`; the documentation recommends writing both. A user method with a matching name but another signature is the normal "does not satisfy" error, never silently ignored.
4. **Built-in types.** `bool` and every integer type are `Eq`, `Ord`, `Hash` (false before true). `text`: by bytes; `compare` equals `text.compare`; `hash` is the hash the runtime uses today. `float`/`f32`: `Eq` and `Ord`, not `Hash`. `==` and `<` on floats stay IEEE (NaN is unequal and unordered); the `compare` method is a total order (NaN after every number and equal to NaN, `-0.0` equal to `0.0`) so sorting never loops or crashes, and `eq` on a float is IEEE `==`. This inconsistency is documented: sorting with NaN is deterministic, looking up a NaN in a sorted map is unspecified but memory safe. Optional `T?`: `nil` equals `nil` and is smaller than any value, otherwise `T`'s rules. `[]T`: elementwise; `compare` is lexicographic, a shorter prefix first; `hash` folds in order. `Map<K, V>`: `Eq` when `K` and `V` are `Eq` (same keys with equal values, order irrelevant), `Hash` when `V` is also `Hash` (sum of per-entry hashes, so order does not matter), never `Ord`. Pointers, functions and channels are not `Eq` through this mechanism (whatever `==` does on them today is kept; task 2.1 records it).
5. **Identity types.** `new T`, `shared T` (from `add-weak-refs` and `add-threads-and-shared`) and `#[shared]` records hold a reference. They are `Eq` and `Hash` by identity (same object) unless the type defines `eq` or `hash`, in which case the user's methods are used. They are not `Ord` unless `compare` is defined, because addresses are neither stable nor meaningful. Weak references are not keys.
6. **Operators.** `binary` and `binary_core` keep the built-in code for scalars and text. For any other operand type, `a == b` calls the type's `eq` and `a != b` its negation; `<`, `<=`, `>`, `>=` call `compare(a, b)` and compare the result with 0. Both operands must have the same type. In a generic body the `Ty::Param` check changes from "never" to "allowed when the bound provides it": `Eq`, `Ord` and `Hash` give `==` and `!=`; `Ord` also gives the ordering operators; the call dispatches statically per instance, like other bound calls. A type that cannot provide the operator produces "operator '<' is not defined for Point: Point is not Ord (field `x: Bag` has no compare)". `x == nil` on optionals keeps its meaning.
7. **Runtime map.** Keys that are `text` or integers keep flags 1 and 0 and the existing code. A new flag bit `4` means "general keys": the map object grows two slots, a hash function and an equality function, which are the addresses of compiler-generated thunks that take borrowed keys in `rcx`/`rdx` and return a 64-bit hash or a bool. `new_map` passes the two addresses to `rt_map_new`; `rt_map_hash` and the comparison in `rt_map_find` branch on the bit and call the thunks. A second bit `8` says keys are heap objects, so `rt_map_set` retains an inserted key and `rt_map_remove`, `rt_map_clear`, `rt_map_release_all` and `rt_drop_map` release it (text keys already do this through bit 1; this generalizes it). One thunk pair is generated per distinct key type (deduplicated through `inst_funcs`) and only when the program uses such a map; each calls the type's `hash` and `eq`, derived or user-written. A key type that is a type parameter reuses the same path through the instance. Alternative considered: write the map in Brasa in `std`. Rejected for now: it would touch every map operation, literal and iteration site; the runtime stays and costs one indirection only for general keys.
8. **Mutating keys.** A key is stored by the rules of assignment (records not declared `#[shared]` are copied in; `#[shared]` and `new` keys are stored by reference). Mutating the hashed fields of a shared key after insertion makes lookups unspecified (never memory-unsafe); this is documented.
9. **Std.** `std/set.br`: `Set<T: Hash>`; a bad element gives the map key error. `std/sorted.br`: `sorted.map<K: Ord, V>()` and `sorted.set<T: Ord>()` order with `a < b`; `map_by` and `set_by` stay for custom orders such as descending; `int_map`, `text_map`, `int_set` and `text_set` are deleted and their callers rewritten. `std/list.br`: `sort<T: Ord>(xs)` (stable, the algorithm of `sort_by` with `<`) and `contains<T: Eq>(xs, x)`; `sort_by` and `find` stay. `std/derive.br` holds the derivation and `hash_combine`.
10. **Errors.** The key error becomes "`Point` cannot be a map key: `Point` is not Hash because field `x: float` is not Hash", and for a float "float cannot be a map key: float is not Hash because NaN is not equal to itself", replacing "keys are text or integers". The tests that assert the old text are updated in this change.

## Risks / Trade-offs

- [Derivation depends on a reflection API that is not final] -> Task 1.1 re-reads `add-comptime-reflection` before writing `std/derive.br`; if reflection is not ready, the compiler expands the derivation itself with the same behavior, and the Brasa version replaces it later without changing the spec.
- [Recursive types (a record holding a list or optional of itself) make derivation recurse forever] -> derivation emits real recursive methods, memoized per type, with a test for a tree record.
- [A thunk call per hash and compare is slower than the inline text and integer paths] -> those paths stay as they are; a test with 100,000 record keys must finish within a few seconds.
- [Changing operators on records could change programs that relied on the current record `==`] -> task 2.1 reads what `==` does on records today; pre-1.0 policy allows the break and every use in the repository is rewritten.
- [Overriding `eq` without `hash`] -> excluded from `Hash` by decision 3, so the mistake is a compile error at the map, not a wrong lookup.

## Migration Plan

Land in order, suite green at each step: (1) `Self` and the prelude interfaces with structural checks, (2) derivation, and operators on user types and bounded `T`, (3) general-key maps in the compiler and runtime, (4) rewrite `set`, `sorted`, `list`, examples, tests and docs, (5) delete the old constructors and the old message. Pre-1.0 policy: no compatibility shims. Rollback is reverting the commit.

## Depends on

- `add-comptime-reflection`: field and variant iteration used by `std/derive.br`. Required.
- `add-int-long-aliases`: `long`, the hash type. Required.
- `add-weak-refs`, `add-threads-and-shared`: `shared T` identity rules; the tests for `shared T` are added when those land, the rule is stated now.
- `remove-interpreter`: removes the interpreter parity requirements and `MapVal`; order is free, and the interpreter tasks below are void if it lands first.
- `add-direct-pe-output`: independent, but the map runtime text feeds both outputs, so the map tests are run on both outputs after it lands.
- `add-text-bytes-and-char` (a `char` or `bytes` type would get the integer or text rules) and `add-copy-on-write` (copy semantics of stored keys): no scope overlap, rules adapt when they land.
