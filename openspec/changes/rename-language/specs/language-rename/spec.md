## Purpose

Renaming the language in one repeatable, reviewable step, and proving afterwards that nothing of the old name is left and that the language behaves exactly as before.

## ADDED Requirements

### Requirement: One input, every form derived
The rename tool SHALL need only the new display name (for example `Zorbo`) and SHALL derive from it every form the repository uses: the display form, the lower-case identifier, the upper-case environment prefix, the command name (identifier plus the `-parse` suffix the command has today), the crate and library name, the assembly symbol prefix, the VS Code extension, language and setting identifiers, and the window class. A name that is not a valid identifier (it must start with a letter and use only letters and digits) SHALL be refused with a message before anything changes. Optional switches SHALL override derived forms (`--ext` for the source file extension, `--repo` for the repository slug, `--publisher` for the extension publisher).

#### Scenario: Deriving the forms
- **WHEN** the tool is given `Zorbo`
- **THEN** its plan shows `Zorbo`, `zorbo`, `ZORBO`, `zorbo-parse` and `ZORBO_UI_SCRIPT` where the repository now has `Brasa`, `brasa`, `BRASA`, `brasa-parse` and `BRASA_UI_SCRIPT`

#### Scenario: A bad name
- **WHEN** the tool is given `9lives` or `two words`
- **THEN** it refuses with a message that says what a name may contain, and nothing changes

### Requirement: Dry run first, then apply
The tool SHALL by default change nothing and print every file or folder it would move and every line it would replace, with counts per file. Applying SHALL be an explicit switch, SHALL refuse to run when the working tree has uncommitted changes (unless forced), and SHALL move files with `git mv` so that history follows them. Running it a second time with the same name SHALL change nothing.

#### Scenario: Dry run
- **WHEN** the tool runs without `--apply`
- **THEN** the working tree is byte-for-byte unchanged and the output lists the planned moves and replacements

#### Scenario: Repeating
- **WHEN** the tool is applied twice with the same name
- **THEN** the second run reports nothing to do

### Requirement: What is rewritten and what is kept
The tool SHALL rewrite the name, in every letter case and in identifiers (`brasa_start`, `BrasaWindow`, `brasa-os`, `brasa-parse`), in tracked text files, and SHALL rename files and folders whose names contain it (`brasa.ebnf`, `brasa-ffi.md`, the grammar file). It SHALL include `openspec/specs/` and the active changes in `openspec/changes/`, and SHALL NOT touch `openspec/changes/archive/`, `.git`, `target/`, `Cargo.lock` (it is regenerated by the build) or binary files. Text that tells the story of the old name SHALL NOT be rewritten blindly: the tool SHALL list those places (README, GOVERNANCE and the site pages that explain what the name means) as manual work and leave their text alone.

#### Scenario: Archive untouched
- **WHEN** the tool is applied
- **THEN** no file under `openspec/changes/archive/` differs from before

#### Scenario: Manual places are reported
- **WHEN** the tool is applied
- **THEN** it ends with a list of the files that contain the story of the old name, with line numbers, which a person must rewrite

### Requirement: Nothing of the old name is left
After the rename, no tracked file outside `openspec/changes/archive/` SHALL contain the old name in any letter case, and no tracked file or folder name SHALL contain it, except lines and files listed in an allow-list that the repository keeps in one place (for example a "formerly known as" note). A test SHALL fail when such an occurrence appears, and SHALL name the file and line. Before the rename the test SHALL only exercise the tool's matching rules, so the suite passes.

#### Scenario: A leftover
- **WHEN** a file still says the old name after the rename
- **THEN** the leftover test fails and names the file and the line

### Requirement: Behavior is unchanged
The rename SHALL change names and no behavior: the whole test suite (Windows, and Linux under WSL where available), the documentation check, the formatter check and the extension tests SHALL pass after it, programs SHALL compile to the same code except for the renamed symbols, and `examples/` SHALL build and print the same output. The rename SHALL be rehearsed on a throw-away copy with a dummy name, with all of these passing, before it is done for real.

#### Scenario: Rehearsal
- **WHEN** the tool is applied to a copy with the name `Zorbo` and the full suite is run in that copy
- **THEN** every test passes

### Requirement: The names users see
After the rename, the command, the crate and library name, the environment variables, the `ui` window class and default alert title, the language server's name and diagnostic source, the VS Code extension (identifier, display name, language id, grammar scope, setting keys, command, output channel, `.vsix` file name), the generated-assembly banner, the usage text and the documentation site SHALL all use the new name, and the documentation SHALL say once, where readers look first, that the language was formerly called by the old name, and which commands, variables and settings were renamed.

#### Scenario: The command
- **WHEN** the project is built after the rename
- **THEN** the compiler executable has the new command name, `--help`-style usage text shows it, and the old command name does not exist

#### Scenario: The extension
- **WHEN** the extension is packaged after the rename
- **THEN** its identifier, settings (`<name>.server.path`, `<name>.server.enabled`, `<name>.trace`) and command (`<name>.restartServer`) use the new name

### Requirement: A name checklist before the rename
The repository SHALL contain a checklist for choosing the name, covering the availability of the crate name, the GitHub organization and repository name, the extension publisher on the VS Code Marketplace and Open VSX, a domain for the site, collisions with existing languages, tools and commands, the length and typing of the command, and whether the source file extension still fits, and the rename tool SHALL print a reminder of it before applying.

#### Scenario: Reminder
- **WHEN** the tool is applied
- **THEN** it first prints the checklist items and the name it is about to use, and asks for `--yes` to continue
